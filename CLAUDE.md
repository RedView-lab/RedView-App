# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

RedView is a 3D route-planning / analysis app for ultra-cycling and bikepacking (React 19 + TypeScript + Vite SPA on Mapbox GL JS v3). It is French-first: the docs (`docs/`: architecture and plans, dated audits in `docs/audits/`, index in `docs/README.md`), comments and commit scopes are largely in French/English mix. Commits follow conventional-commit style with a scope, e.g. `fix(chart,map): ...`.

## Commands

```bash

npm run lint         # eslint (flat config, TS/TSX + server.mjs/server/*.mjs), cached; lint:prune after fixing a frozen error
```

**Tests.** Unit tests are Vitest (`vitest.config.ts`, standalone: it must never import `vite.config.ts`, whose dev plugin loads `.env`, starts BRouter/POI and opens the SSH tunnel). They sit next to the module (`foo.ts` → `foo.test.ts`, explicit `import { describe, it, expect } from 'vitest'`), server ones in `server/lib/__tests__/`, `server/multiplayer/` and `api/_lib/__tests__/`, the tile Service Worker's in `test/service-worker/` (`public/` is served as-is and cannot hold them); `.dockerignore` keeps them out of the image. Write them for pure business logic first (security boundaries, persistence, routing math, UI rules). The `script-test-bench/` benchmarks (run with `tsx`) stay for heavy/perf/real-data regressions, and `scripts/test-*.mjs` are ad-hoc probes against VPS services. Type-checking is `tsc -b`: app (`src`), `vite.config.ts`/`vitest.config.ts`, and `api/` + server tests (`tsconfig.api.json`, `allowJs` so `server/*.mjs` imports are typed).

**Lint ratchet.** Pre-existing ESLint errors are frozen in `eslint-suppressions.json` (ESLint bulk suppressions): any new error fails `npm run lint`; after fixing a frozen one, `npm run lint:prune` (the gate fails on stale suppressions too). `_`-prefixed names are intentionally unused (same rule as tsc's `noUnusedParameters`). Never add a suppression to get a change through: fix the error.

`npm run deploy` deploys committed work only: it stops at once on a dirty working tree (several sessions share this repo; the former `git add .` swept everyone's work in progress into one undescribed commit) — commit by topic first, or `npm run deploy -- --commit-all "<type(scope): message>"` for the old commit-everything behaviour. It then runs the quality gate (`scripts/quality/check.mjs --full`) on that tree, then compares the production Appwrite schema with `scripts/appwrite/setup-appwrite-schema.mjs` (`--check`, read only, needs `APPWRITE_API_KEY` in `.env`; a new collection/attribute/bucket must be applied with the same script before deploying code that uses it); on failure nothing is committed or pushed (`--skip-checks` exists for emergencies only and leaves a `Checks-Skipped: true` trailer). It then pushes to `origin/main`, and triggers the Coolify deploy over SSH to the production VPS. Never run it unprompted. `npm run rollback` lists the images Coolify keeps per commit (app and real-time server, the running one marked); `npm run rollback -- <sha> [--app-only]` restarts that already-built image (no build, both services by default; Coolify helpers shared in `scripts/release/lib/coolify.mjs`) — code only, never schema or data, and `main` still holds the bad commit: revert it before the next deploy. Same rule: never unprompted. CI (`.github/workflows/ci.yml`) runs the same `check:full` on every push and PR to `main` (tsc build info and the ESLint cache — `--cache-strategy content`, a checkout resets mtimes — are cached after `npm ci`, which wipes `node_modules`).

### Rust/WASM prediction engine

`vendor/redviewalgo/` is a Rust crate: the cycling moving-time engine v2 (`src/cycling/`: physics + behaviour simulated on a ~10 m grid — power policy by gradient, descent comfort speed, corner radius √(a_lat·R) with braking/re-acceleration, surface, walking, warm-up/endurance; level presets in `cycling/presets.rs`; FIT calibration with built-in cross-validation in `cycling/calibrate/`), the running engine (`src/running/`, KNN), FIT/GPX parsing. The cycling engine returns **moving time only and takes no pauses** — pauses belong to the app's schedule (`pauseAwareSchedule`). Bump `ENGINE_VERSION` (`cycling/mod.rs`) and `CYCLING_ENGINE_VERSION` (`fitPredictor/engine/version.ts`) together when results change: older persisted bike predictions are recomputed.

Rebuild with `powershell -File vendor/redviewalgo/build.ps1` (no wasm-pack needed): it calls the rustup toolchain directly, checks the wasm-bindgen CLI version against `Cargo.lock`, runs the unit tests on wasm32 under Node (`wasm-bindgen-test-runner`; in test modules shadow `#[test]` with `wasm_bindgen_test` under `cfg(target_arch = "wasm32")`, native tests can't link on windows-gnu), then writes the JS glue + `.wasm` into `src/features/fitPredictor/engine/pkg/` and copies `redviewalgo_bg.wasm` into `public/`. `-OutDir <dir>` builds elsewhere without touching the app; `-SkipTests` skips tests. Both outputs are committed; `target/` is ignored. The frontend talks to it only through a Web Worker (`fitPredictor/engine/api.ts` → `worker.ts`; bike path in `itineraryPanel/hooks/useItineraryFitRuntime/cycling.ts`).

`vendor/redviewlaz/` is a second, small Rust crate (laz-rs): the LiDAR viewer's COPC chunk decoder, with LAZ 1.4 selective decompression (only X/Y/Z, classification, intensity, RGB; GPS time, scan angle, point source, user data and flags skipped) — ≈ 2× laz-perf on IGN tiles, byte-identical output. `powershell -File vendor/redviewlaz/build.ps1` (same toolchain recipe and wasm32 tests) writes `src/features/lidar/lib/laz/pkg/` (committed; Vite emits the `.wasm` as an asset). The module is compiled once on the main thread (`lib/laz/redviewLazModule.ts`, Firefox's CSP refuses compiling in a worker) and handed to the decode workers; laz-perf stays the fallback (no module, or a decode error). `lib/laz/redviewLaz.test.ts` compares both on two real IGN chunks.

Accuracy bench: `npm run bench:pace` (`script-test-bench/pace-accuracy/`, real Chamonix→Paris FIT rides + synthetic physics scenarios, non-zero exit on a hard-criterion failure); `npm run bench:pace:prep` fetches OSM tags (prod BRouter proxy) and historical ERA5 wind once into a git-ignored cache (wind from a throwaway Open-Meteo container reading Open-Meteo's CC BY open data on AWS, `PACE_WIND_ARCHIVE` — never the public API; commands in `lib/wind.ts`; without it R9 is reported « non mesuré »); `npm run bench:pace:realism` compares famous climbs (BRouter geometry, IGN elevation), flat speeds and GT20 against public references. FIT files are not in the repo (`PACE_FIT_DIR`).

Routing bench: `npm run bench:routing -- --label <name>` (`script-test-bench/routing-quality/`) runs ~660 scenarios (9 bike presets + variants + running/trail, 15–1 200 km) through the real client + `api/brouter.ts` pipeline against prod BRouter, which needs an SSH tunnel (`ssh -i ~/.ssh/oracle_brouter.key -N -L 27777:127.0.0.1:17777 opc@141.145.220.99`; nginx `/brouter` is closed to the public). It stays sequential (`--concurrency` ≤ 2) to keep prod's 4 BRouter threads free, and resumes an interrupted run. `bench:routing:sweep` calibrates the A* coefficient, `bench:routing:compare -- --before a --after b` writes `reports/routing-quality/ROUTING_QUALITY_REPORT.md` with guard-rails (non-zero exit on failure), `bench:routing:report` the HTML page. Latency through the tunnel depends on the client's line: for faithful numbers build `routing-quality/vps/build-vps.mjs` (single-file bundle, Node ≥ 20) and run it on the VPS next to BRouter.

## Architecture

### Four deployable pieces
1. **Frontend SPA** (`src/`) — two Vite HTML entries: `index.html` (app) and `viewer.html` (served at `/viewer`).
2. **Node "serverless-style" API + static server** — `api/*.ts` are Vercel-style handlers (`(req, res)` with `req.query`, `req.body`, `res.status().json()`). They are executed by **two separate adapters that must stay in sync**: the `redviewDevApiPlugin` in `vite.config.ts` (dev, via `ssrLoadModule`) and `server.mjs` (prod, Docker/Coolify, `node:22-alpine`, `Dockerfile`). In the image, `server.mjs` and every route are bundled by esbuild into `dist-server/` and run by plain `node`, no tsx (`scripts/build/build-server.mjs`: routes as `dist-server/api/<route>.mjs`, `process.env.REDVIEW_SERVER_BUNDLE` defined at build time; only package.json `dependencies` stay external and are installed in the image — browser-only packages are `devDependencies`, and a bundled devDependency fails the build). Static files are precompressed at build (`scripts/build/precompress-dist.mjs`, rule in `server/lib/static-compression.mjs`): `server.mjs` serves the `.br`/`.gz` variants by negotiation and never compresses at runtime when they exist. API responses are compressed by `server.mjs` instead (`server/lib/api-compression.mjs`: JSON/text ≥ 1 KiB, brotli 4 or gzip 6, off the event loop above 64 KiB) unless the handler already set `Content-Encoding`; the dev plugin does not compress. Every server in-memory cache is bounded in bytes with `server/lib/byte-lru.mjs` (containers have memory limits) — a new cache must use it; a bounded `Map` that evicts at its head takes the key from `server/lib/oldest-key.mjs`, never `keys().next()` (V8 rescans every deleted slot from the table start: ~10 µs per eviction at 50 000 keys). Both map `/api/<name>` → `api/<name>.ts`, collapse `/api/openmeteo/*` and `/api/weather/*` (server.mjs also `/api/brouter/*`) onto one file, and both serve the tile fallbacks a page without the Service Worker asks for (`/radar-tiles`, `/slope-tiles`, `/altitude-tiles`; `/dem-tiles`, `/vhr-tiles` and `?pf=1` prefetches answer 204) through `server/lib/tile-fallbacks.mjs`, and decode `req.query`/`req.body` through `server/lib/api-request.mjs` (null-prototype query). A new API route shape usually needs changes in both places; a new tile family goes into `tile-fallbacks.mjs`. Path normalisation, `/api` route resolution (no `_lib/`, no encoded `..`), body-size limits (`bodyLimitFor`), client-IP/rate-limit keys, tile-coordinate validation, the radar host allowlist and the `/api/pointcloud` upstream allowlist (LiDAR sources without CORS: AHN sub-tiles from GeoTiles, DHMV II strips from EODaS OpenLidar — streamed with `Range`, never buffered) live in the shared `server/lib/http-security.mjs`, used by both adapters — change them there, not in each adapter. `server.mjs` also owns in-memory rate limiting and security headers; the CSP lives in `server/lib/csp.mjs` (`buildCspHeader`, set on HTML pages and worker scripts; no `'unsafe-eval'`: WebAssembly only needs `'wasm-unsafe-eval'`; violations are reported to GlitchTip's security endpoint) — **any new external host the browser talks to (tile servers, APIs) must be added to that CSP**; `bench:lidar-engines` serves the viewer under it in Chromium and Firefox and fails on any violation.
   **Observability** (prod adapter only; the dev plugin has none on purpose). Errors go to self-hosted **GlitchTip** (`errors.redview.tech`, Sentry protocol — not Sentry). Front: `@sentry/react` in `src/main.tsx`, release = build id; every page URL and breadcrumb URL is cut to its path before sending (`shared/lib/errorReportScrub.ts`: reset links carry `?userId&secret&email`, requests carry coordinates). The build id has one source, `server/lib/build-id.mjs` (Vite define, sourcemap tag, server release). Sourcemaps are built `hidden`; the Docker builder runs `scripts/build/upload-sourcemaps.mjs`, which uses `glitchtip-cli` (pinned SHA-256; sentry-cli's chunked upload does not work with GlitchTip) to inject debug IDs into `dist/assets` only (never the `public/` SW scripts), upload the maps, then delete every `.map`. `server.mjs` also 404s any `.map`. Server: `server/lib/observability.mjs` (`@sentry/node`, only with `SENTRY_DSN_SERVER`, errors only, tags route/request id/method set in a local `withScope`, scrubbed of headers/query/body/IP, flushed on SIGTERM) and `server/lib/request-logging.mjs` (pino-http: one JSON line per request on stdout with method, **normalised** route (`normalizeRoutePath`, which the server sets on `req.redviewRoute`), status, duration, `X-Request-ID` (a safe incoming one is kept, otherwise a UUID; echoed in the response and exposed to handlers as `req.requestId`) and build id; never the raw URL, query or headers; a 2xx `/health` is silent, static assets log at debug, `LOG_LEVEL`). `api/poi.ts` forwards `X-Request-ID` to the POI server, whose Fastify logger writes the same line shape (`server/poi-server/server.js`).
3. **Real-time co-editing server** (`server/multiplayer/`, Coolify service `redview-multiplayer` built from `Dockerfile.multiplayer` — the image runs the esbuild bundle `dist-server/multiplayer.mjs`, collab engine from `src/` included —, deployed by `npm run deploy` before the app): its port is published on `127.0.0.1:17790` only, and the **host nginx** (`/etc/nginx/conf.d/app.conf`, which also proxies the app to `127.0.0.1:3000`) routes `/multiplayer` to it with WebSocket headers — public traffic never goes through Coolify's Traefik labels. The app shows « Partager » only when `/multiplayer/health` answers `{"ok":true}` (that is all it answers; an unknown path returns the SPA's `index.html` with 200). Metrics (rooms, clients, journal/checkpoint latency, errors, shadow validation, event-loop delay, heap) are served on the container's internal port 17791 only, never proxied: `sudo docker exec $(sudo docker ps -q -f name=krejrvgvs2w5kmfo27rutffz) wget -qO- http://127.0.0.1:17791/metrics.json` (`/metrics` = Prometheus text). Errors go to GlitchTip when `SENTRY_DSN_SERVER` is set on that service (same `server/lib/observability.mjs`). See `features/collab` below.
4. **VPS microservices** (Oracle VPS behind nginx, reached through the `api/` proxies via `BROUTER_UPSTREAM`, `POI_UPSTREAM`, `WEATHER_UPSTREAM` — see `.env.example`):
   - BRouter standalone (port 17777) — routing engine; `api/brouter.ts` whitelists query params and uploads dynamic BRF profiles. In dev, `scripts/dev/start-dev-services.mjs` starts a local one if a sibling `../redview-brouter` checkout exists. The frontend generates a fresh ~500-line BRF profile from UI sliders on each change (`brf-template.ts`); see `docs/architecture/routing.md`. Search is always single-pass (`pass2coefficient=-1`); the A* `pass1coefficient` is set per request from the profile's cost per metre (estimated in `brf-template/values.ts`, then learned from responses) and the distance (`lib/brouter/api/searchCoefficient.ts`, bounded server-side by `api/_lib/brouter-search.ts` — same distance steps on both sides, enforced by `searchCoefficient.test.ts`). Every itinerary is routed with its generated profile, even with neutral sliders — never a stock BRouter profile (`routing-resolver.ts`; an upload failure is retried once, then reported). Sections longer than ~180 km are routed coarse first, then refined between anchors placed on the coarse track (`routing/long-distance-anchors.ts`, orchestrated in `useItineraryBrouterRouting/resolveRouteRequest.ts`); a slow fine search is hedged by a greedier one after a distance-based delay (`customProfileFetch.ts`), and when it still times out the same anchor method runs with tighter anchors (then a greedier coarse search) instead of any fallback profile. Timeouts stop at response headers, not download. Local edits (move/insert/remove a point, forbidden zone, on BRouter or imported GPX routes alike) only reroute a window of the stored route around the edit, ±12 km first, widened to ±80 then ±200 km and the real bounds only when the new route does not rejoin the old one (`narrowRoutePatchToEdit`, `WINDOW_STEPS_M` in `routeSegments.ts`: search time grows much faster than length, a ±80 km first window cost seconds per drag); a pending patch is routed by a per-itinerary job (`ensurePatchJob` in `useItineraryBrouterRouting`), for the selected itinerary and the others alike, so an edit on a non-selected itinerary, or a selection change mid-reroute, is never left unrouted (append and full recompute stay on the selected one); patch bounds taken on the route carry their `distanceM`. **A stored route never contains a straight line** (they end up in the GPX export): every join of route pieces (patch, extension, request legs, recalculation, merge) must meet within `ROUTE_SEAM_TOLERANCE_M` (`lib/routes/route-continuity.ts`); a patch's intermediate bounds are requested on the stored track (`anchorRoutePatchBound`) and spliced where the routed piece really rejoins it (`planRouteSplice`), a `start`/`end` bound replaces everything before/after it, and a join that fails widens the window then falls back to a full recompute (`RouteSeamError`), never a line. Start/finish placed on the route crops it without routing (`cropRoutePoints`, `placeRouteEndpoint`); the LiDAR viewer's freehand gestures on a routed itinerary are translated into the same app edits (`lidarViewerRouteEdit.ts`); GPX segment jumps and sparse `<rte>` files are routed at import (`importedGpxGaps.ts`); old start/end artifacts are dropped on normalisation (`repair-route-endpoints.ts`). Checks: `npx tsx script-test-bench/route-continuity/run.ts` (prod BRouter through a tunnel) and `node script-test-bench/route-continuity/e2e.mjs` (needs `npm run dev`). `api/brouter.ts` compresses route GeoJSON itself (brotli/gzip, kept compressed in its cache), so `server.mjs` leaves those bodies alone.
   - `server/poi-server/` — Fastify + SQLite/R*Tree POI server (port 17778), built by `server/poi-ingest/`.
   - `server/weather-daemon/` — Python GRIB ingest + tile server (systemd units, nginx conf).
   - Self-hosted Open-Meteo (`server/vps/open-meteo/docker-compose.yml`, 127.0.0.1:8080, nginx `/openmeteo/`, `OPENMETEO_UPSTREAM`): the only source of point forecasts (`/api/openmeteo`, route weather, wind, map context menu) and of the snow model's weather history — **never the public api.open-meteo.com** (non-commercial licence; the browser cannot reach it, CSP). Scope decided with the user: France and neighbours, J+4, ≤ 5 GB — Météo-France AROME France 0.025° (51 h) + ARPEGE Europe 0.1° (4 days) synced locally (`sync … --execute` prunes old files; 62 days of the snow model's 5 ARPEGE variables), ~1.9 GB, no on-demand S3 reads (≥ 60 s for a 200-point request). Clients ask `models=meteofrance_seamless` (`OPENMETEO_MODEL`), horizon `OPENMETEO_FORECAST_DAYS` = 4; `api/_lib/openMeteo.ts` validates the model (legacy `best_match`/AROME HD mapped), clamps days and caps 200 locations. No climate (CMIP6) and no elevation API: route elevation outside France comes from Terrarium tiles (`shared/lib/terrarium.ts`). A new variable or model must be added to the sync and fit the budget.
   - Host configuration (BRouter unit and its 3 GB heap, systemd resource drop-ins, sysctl, journald, Docker `daemon.json`, Appwrite compose override) is versioned in `server/vps/` — its README gives where each file goes, how to apply/roll back, and the **Always Free memory floor** (Oracle reclaims an idle A1 instance when CPU, network *and* memory stay under 20 % for 7 days; memory is the only one above: keep used RAM ≥ 25 %). `bash scripts/vps/perf-snapshot.sh <label>` takes a read-only before/after snapshot.
   - **Service watch** (`server/vps/watch/`, README = checks and alert rules): `redview-watch.timer` runs `/usr/local/sbin/redview-watch run` every 5 min — 15 checks through the public URLs (app `/health` and page, `/multiplayer/health` = `{"ok":true}`, a BRouter route with jittered points so the API cache can't answer, self-hosted Open-Meteo source + ≥ 48 h of forecast ahead, POI, Appwrite, `/s/x.js`, Umami, GlitchTip, TLS ≥ 14 days) and on the host (no `unhealthy`/`restarting` container, last backup < 30 h and last drill OK, disk < 90 %, used RAM ≥ 25 % Always Free floor); « PANNE » e-mail through Resend after 2 consecutive failures, reminder every 6 h, « Rétabli » at the end; `HEARTBEAT_URL` (healthchecks.io-style) pinged each pass is what sees the VPS itself down. A new public service or VPS dependency gets a check there; `sudo /usr/local/sbin/redview-watch check` shows them all.
   - **Backups** (`server/vps/backup/`, README = disaster-recovery runbook): `redview-backup.timer` runs `/usr/local/sbin/redview-backup run` nightly at 02:30 UTC — logical dumps made inside each DB container (Appwrite MariaDB without the `_1_audit` data, Coolify/GlitchTip/Umami PostgreSQL), Appwrite volumes, `/opt/appwrite/.env` (its `_APP_OPENSSL_KEY_V1` decrypts stored files), `/data/coolify/source/.env` (APP_KEY), `/etc`, services and a system manifest → restic (encrypted, deduplicated) → Google Drive `RedView-Restic` through rclone (own OAuth client, scope `drive.file`: the VPS token only sees what rclone created); retention 7 daily / 5 weekly / 12 monthly. `redview-backup-verify.timer` (Sun 04:30 UTC): prune, `check --read-data-subset n/12`, a real restore drill (dumps reloaded into throwaway tmpfs containers, row counts compared; 40 Appwrite files compared byte for byte; critical files present) and a weekly report e-mail; any failure or a > 30 % shrink e-mails through Resend (`OnFailure=redview-backup-alert@`). The restic password must also live off the VPS (dev PC `~/.redview/backup/`, password manager). Files installed on the host keep their SELinux context — always `install` + `restorecon` (`install.sh`): a `cp`/`mv` from `/tmp` (`user_tmp_t`) kept the previous cron silently dead for 16 days. `sudo` has no `/usr/local/sbin` in its PATH on Oracle Linux: call the full path.

### Frontend structure (`src/`)
- `App.tsx` handles bootstrap: Appwrite session, subscription gating (currently all registered users get access during open beta; non-subscribers are labelled `demo`), mobile block, then lazy-loads `pages/Dashboard`. **Initial load:** `index.html` paints a static splash (`.rv-boot`, inline styles, OS theme until `data-rv-theme` is set) that `BootstrapScreen` re-renders identically, so there is no white page. The Dashboard shell (project browser) loads without the 3D editor: `DashboardEditor` is `lazy()` (`pages/Dashboard/editorLoader.ts`), prefetched when the browser is idle, when a project card is hovered (`data-rv-project-card`) and as soon as a project starts opening. The shell must import concrete modules, never the `map3d`/`controlPanel` barrels, and the LiDAR provider only holds a slot (`lidarManagerSlot.ts`: the `LidarManager` is created by `useLidarManager()` in the editor and destroyed with the Dashboard). `npm run bundle:check` (part of `check:full`) fails if mapbox-gl, mapbox-gl-draw, copc, proj4 or the editor land on that critical path, or if it exceeds 300 KiB brotli (271 KiB measured, 1 075 KiB before the split).

- LiDAR rendering (`lidar/viewer`): tiles stream as additive octrees from the OPFS LOD cache (`lib/lodCache.ts` v2, 16 B/point: position, class, intensity, RGB and the cell-filtered RGB/intensity a node shows where none of its children is drawn, so coarse levels look like a mip level instead of salt-and-pepper samples; a v1 cache is upgraded on open, no decoding). `SceneLod` selects nodes by projected spacing under the adaptive moving budget (`lodBudget.ts`); once the camera stops, `lod/restRefinement.ts` grows the budget towards ~50 ms of GPU per still frame (platform `restMaxBudget`), then accumulates 16 sub-pixel-jittered frames in linear light (`renderScene({ accumulate })`) and idles. The DTM mesh is drawn per 128-quad chunk at the level the view needs (`renderer/terrainLodCore.ts`, shared by both backends: stitched edges, coarse chunks pushed back along the view ray by their height error so they never hide a point; lit with the points' `shadeSurface`): drawn whole (19 M triangles for 9 tiles) it held an iGPU's point budget at 1.5 M. `npm run bench:lidar-shots` captures fixed views of a real multi-tile scene (before/after a rendering change, `--dist` for a kept build) and `bench:lidar-fps` takes `LIDAR_TILES_DIR` for a 9-tile scene (`--cold` drops the derived caches first and prints the load-step timeline of a first opening: decode, ortho colouring, LOD build + OPFS write, written through a sync access handle in the worker). A first load runs through a two-stage pipeline (`session/sceneMemoryBudget.ts` `TileLoadPipeline`): decode (every decode worker; they post their points in 1 M-point batches copied straight into the tile's arrays and stop when done, the compressed file is dropped once split — `workers/copcDecodeWorker.ts`) + colourise + ground copy, then LOD build + OPFS write (one worker); the next tile decodes while the previous one builds, one tile per stage, when both stages fit 40 % of `deviceMemory` (38 B/point each, counts read from the LAS headers; a tile alone always runs). The 9-tile scene: 7.65 GB with three tiles at once, then 4.68 GB and 133–171 s one tile at a time (parts, assembled arrays and eight never-shrinking WASM heaps at once), now 3.8 GB and 100–109 s on battery against 140–172 s for the sequential load (interleaved A/B, 2026-10-07), byte-identical caches; a one-time cost, cached reopen 2.1 s. Storing a downloaded tile asks once for persistent storage (`requestPersistentStorage`: best-effort storage is evicted under disk pressure, or after 7 idle days in Safari) and a full quota fails the download (`StorageFullError`, final for the URL loops: `isFinalDownloadError`) — the viewer, another page, can only open tiles in the origin's storage; a LOD cache that cannot be written is streamed from memory (`bench:lidar-fps -- --quota <MB>`).
- **Two rendering backends, one viewer** (Linux compatibility). The viewer only talks to the `LidarRenderer` interface (`viewer/renderer/sceneRenderer.ts`), implemented by `WebGpuLidarRenderer` (`viewer/renderer.ts`) and `WebGlLidarRenderer` (`viewer/renderer/webgl/`), each a lazy chunk loaded only when chosen. **Never read a WebGPU global (`GPUShaderStage`, `GPUBufferUsage`…) at module level**: Firefox on Linux has none, and one such constant made the whole viewer throw on import there (`noWebGpuApi.test.ts` imports every renderer module without them). Both draw the same frame: lazy per-node shading (WebGL 2: the WGSL compute pass as a vertex shader captured by transform feedback), instanced sprites with the adaptive size, chunked terrain LOD, overlays, route/analysis meshes, sun trajectory, EDL, reduced resolution while moving, MSAA on discrete GPUs, rgba16f accumulation (needs `EXT_color_buffer_float`, else still frames are not averaged) — so tools, comments, route editing, look-around and snow run on both. `createLidarRenderer` (`renderer/createRenderer.ts`) takes WebGPU when the preflight (`renderer/device.ts`: 8 s adapter / 10 s device timeouts — some Linux Vulkan stacks never answer; fallback and software adapters refused) finds a hardware adapter, else WebGL 2 on a fresh canvas (`renderer/canvas.ts` `claimViewerCanvas`: a canvas keeps its first context type). That is the usual Linux path in 2026: Firefox ships WebGPU on Windows/macOS only, Chrome enables it on Linux for Intel Gen12+ and NVIDIA on Wayland. The GLSL in `webgl/glShaders.ts` is a line-for-line port of the WGSL sharing the std140 `Scene` block (`packSceneUniforms` fills both): **a shading/overlay change goes into both**. WebGL has no clip control in Firefox, so its depth is conventional with the camera's near/far (`camera.getDepthRange()` → `setDepthRange`, linearised by its EDL pass). `?engine=`: absent = auto, `webgl` = WebGL 2, `terrain` = the older textured DTM without points (`viewer-webgl/`), also the last resort when neither backend starts; two GPU context losses within 2 min step WebGPU → WebGL 2 → terrain. The panel's « Moteur » lists the three (WebGPU greyed out with the reason when unavailable). WebGL renderer strings (ANGLE, Mesa, Firefox's sanitised names) map to the same GPU tiers (`resolveWebglPlatformInfo`); CPU rasterisers (llvmpipe, SwiftShader, WARP) get the `software` profile. Without GPU timers (Firefox never exposes them) still frames are judged on the real interval (`FrameClock.lastIntervalMs`, long frames included) and a complete still frame over 200 ms ends the refinement (`restRefinement.ts`). Input is platform-neutral: the tools menu opens on the right-button release and `contextmenu` is always cancelled (Linux sends it on the press), wheel deltas are normalised (`wheelDeltaPixels`: Firefox reports lines). `npm run bench:lidar-engines` (Playwright Chromium + Firefox, `--browsers webkit` for Safari's engine — its Windows build leaves OPFS writes empty, so tiles go to CacheStorage as `saveTile` does after checking the written size; synthetic LAS tile, external network cut; CI job `viewer-linux` on Ubuntu with `--expect-auto webgl`; a browser whose auto engine already is WebGL 2 skips the forced-WebGL case, the same path) checks render, EDL, colour modes, terrain, slopes, sunlight, right click in Linux order, drag-pan, line-mode wheel and `gl.getError()`; `bench:lidar-shots -- --params engine=webgl` compares both backends on a real tile (2026-10-06, tile 0965_6500: mean difference ≤ 0.21/255, same LOD selection).
- `features/snow` is the snow depth of the LiDAR viewers' snow modes (WebGPU and WebGL; heights come relative to the scene centre, hence `altitudeOffsetM`). `runSnowPipeline` loads in parallel the AROME 0.01° analysis (`/api/meteofrance`, ±0.4° × 0.3°; without it — outside its domain, Météo-France down — there is no snow field), `/api/snow-context` (flat-field station depths: SLF IMIS and the Météo-France open hourly `NEIGETOT` of the surrounding départements, streamed and cached server-side, buddy-checked; the BRA snow cover through DPBRA with `METEOFRANCE_API_KEY`, massif outlines in `api/_lib/snow/braMassifs.ts`; 60 days of weather from the self-hosted Open-Meteo) and Terrarium tiles (model orography of every cell, ±7 km far-field DEM); the viewer adds the canopy read from the point cloud. - `centerPanel/flyover` is the 3D route playback (toolbar Play). `FlyoverController` runs outside React: on Play it builds a camera rail once (`engine/cameraRail.ts`, pure functions, cached per route and prebuilt on idle) — route resampled at constant spacing, playback speed curve (time spread by tortuosity and grade at the camera's scale, capped heading rate, bounded relative acceleration, global factor solved for the target duration `22 s·√(L/10 km)`), camera distance tied to speed (constant on-screen flow; it follows the speed smoothed over 2.5 s and slew-limited to 6 %/s of zoom, `framingSpeedMps` — the raw speed dips at every sharp bend and made the camera dive and climb back within a second), zero-phase smoothed centerline/heading (heading smoothing divided by straightness²: hairpins follow the climb axis, laps and U-turns don't spin the camera), relief pitch, and a helicopter weight (tortuous climbs such as Alpe d'Huez: slow orbit on a small arc around the target, a bit higher and steeper; the heading limiter reserves the orbit's rate). Map markers that must stay click-through (`.rvi-analysis-hover-dot`) need a stylesheet `pointer-events: none !important`: Mapbox rewrites the inline `pointer-events` of a marker on every move (`Marker#_evaluateOpacity`).
- Itinerary POIs are one GPU symbol layer (`features/poi/lib/poi-markers.ts`). **Never trust Mapbox's own symbol hit test for them**: it tests the whole sprite image (transparent padding and baked shadows: a 19 px disc in a 66 px image, a pin in an 88×126 px image centred on its tip) and returns overlapping symbols in data order, not drawing order (no `featureSortOrder` with `symbol-sort-key`). Hover, click, the cursor and `queryPoiAtPoint` (Tracer, route split, comments, chart hover) all go through `queryKeyAt`: Mapbox only supplies candidates, then each sprite's mask of drawn pixels (`poi-hit-mask.ts`, alpha ≥ 50 %, chamfer distance field) decides — topmost drawn pixel, else nearest within 3 px; data is sorted in drawing order. Favourite ⇒ pause: starring a POI (map popups, agenda, roadbook) also sets its pause on the row (`durationMin`: the category's Rythme duration, else 5 min), unstarring removes it, unticking the pause sets `0` (`ItineraryPanelContainer/poiFavoritePause.ts`, the single rule). The roadbook's « Agenda » tab is the view id `'timeline'` (persisted, unchanged): every vertical position there goes through `minuteToCanvasTopPx` (hours, grid, blocks, now line, drag), a block's header sits on its top line, and « Jusqu'au suivant » is the riding time to the next point in time.
- `features/map3d` wraps Mapbox (terrain, custom WebGL layers, `hooks/useMap/*`). The map saves its viewport 500 ms after `moveend`; that value comes back as `initialViewport` and `useMap` ignores its own echo (only another viewport is jumped to) — it used to snap back any camera flight started within those 500 ms. Heavy compute lives in Web Workers / WASM (LiDAR `.las/.laz` via `copc` + `laz-perf.wasm`, FIT prediction). **`styledata` handlers must be idempotent** (touch the style only when something is missing or different): every `styledata` flushes Mapbox's terrain drape cache (all proxy tiles re-rendered), and a handler that mutates unconditionally re-fires `styledata` on the next frame — `moveLayer` dirties the style even for a no-op move, so `useLidarSelection` restacking on each `styledata` kept the map re-styling every frame, never idle. `TerrainManager.init()` only calls `setTerrain` when source/exaggeration differ (the anti-flat guards call it on every `styledata`/idle/heartbeat). The style bootstrap (`hooks/useMap/controller`) mutates the style once Mapbox parsed it (`canMutateStyle`), never on `isStyleLoaded()` (which also waits for the sprite, TileJSONs and imports), and waits for that parse without a deadline; every watchdog judging Mapbox's progress (stuck style, force-3d, heartbeat, loading deadline, reload verify…) runs on `controller/visibleClock.ts`, never a wall-clock timer: a hidden page (background tab, minimised or covered window — Vite reloads it there when another session edits a file) gets no animation frame, so Mapbox parses no style (`Style#loadJSON` waits for one), loads no tile and never goes idle.
  `lib/styleLessMapGuards.ts` makes `Map#getSource`/`getLayer` return `undefined` while no style was ever loaded (api.mapbox.com unreachable, token refused or absent): Mapbox reads `this.style.…` and threw, which crashed the whole editor on a GPX import (found by `e2e:journey` without a token).

### Typography & UI density
- **Type scale**: every text size goes through `src/shared/styles/typography.css` (`--rv-font-size-2xs…4xl`, `--rv-font-sans`), whose header holds the role table (panel title 16/600, section/tab 14/600, label 13/500 dimmed, control value/button/menu 13/600, compact toolbars and dense 2-column grids 12/500, caption 11, …). Never write a literal `font-size` or a fluid one (`vw`, `cqi`, `clamp`) in a feature; pick the role's token. Canvas/sprite text uses `RV_FONT_SANS` (`shared/lib/typography.ts`). Rethink Sans is the only font, served by the app (`@fontsource-variable/rethink-sans` files, `@font-face` in `typography.css`) — never Google Fonts: its stylesheet blocked the first paint behind two third-party origins and sent visitors' IPs to Google.
- **Density**: the dashboard is rendered on a logical canvas scaled by `appScale` (`shared/lib/appScale.ts`). Rule: **never below 1:1 on a standard-density screen** — a CSS px already carries the OS scaling and browser zoom, and shrinking gave blurry 8–10 px text on non-HiDPI screens (half-screen 1080p, 1366×768, 1080p laptops at 125–150 %). Up to the 1920×1080 reference the UI is 1:1, above it grows gently (capped at 1.12). Retina exception (`resolution ≥ 2dppx`, read through a media query because `window.devicePixelRatio` is capped for Mapbox in `runtimeProfile.ts`): below the reference the scale takes half the deficit, floor 0.85 (MacBook Air 13" ≈ 0.87, MBP 14" ≈ 0.89) — 1:1 looked oversized on MacBooks and pushed toolbars onto two rows. The scale is applied with CSS `zoom` (`appScaleStyle`, transform fallback only where `zoom` isn't standard), never `transform: scale()`, which resamples text. The LiDAR viewer applies the same scale to its floating panels (`zoom: var(--app-scale)`). Small windows reflow instead (`pages/Dashboard/lib/layout.ts`): side panels shrink, then alternate (`resolveSidePanels`: the last opened stays) when the center column would drop under 560 px; below 846 px of height (`isShortCanvas`) the map tools become a 2-column grid of 32 px buttons and the center panel gets denser/shorter (240 px min). Below 820×500 a dismissible "window too small" overlay shows (`useIsMobileDevice`). Text floor is 11 px (`xs`); `2xs`/`3xs` are for badge digits and map markers only. Toolbars never wrap: the map search + filter chips (`DashboardPlaceSearch`: the search field shrinks first, then the chip labels with an ellipsis, then `--tight` chips; labels are only dropped (`--icons`) on a very narrow map stage, e.g. 1366 px with both side panels open; the steps are computed from the chip list, `PLACE_SEARCH_*_WIDTH`) and the center analysis toolbar (`useToolbarFitDensity`, 8 measured steps ending in ellipsis on every label, full text in `title`). `npm run bench:screens` (needs `npm run dev`: it uses the dev demo account) drives the real dashboard in headless Edge over 15 screens (half-screen 1080p, laptops at 125–150 %, MacBooks, 1440p, 4K, ultrawide…) plus a 1080p window with an ~800 px left panel, and fails on any text under 11 px (11 × 0.85 on Retina), a `transform` scale, a toolbar on two rows, overlapping/overflowing panels, a menu/context menu/resize not aligned with the pointer, a Mapbox canvas not covering its container, or `styledata` events firing while the map is at rest (style-mutation loop).
- **Mapbox under the canvas zoom**: GL JS measures its container with `getBoundingClientRect()` and only compensates CSS transforms; `map3d/lib/mapContainerZoom.ts` patches `Map#_updateContainerDimensions` to divide by the effective CSS `zoom`, so the transform, canvas, `event.point` and `map.project()` are all in the map container's layout px (without it the 3D map covered appScale² of its area on Retina). Code placing DOM from map px works in layout px (`clientWidth`, `offsetWidth`, `event.point`), never `getBoundingClientRect()` sizes; a rect-measured distance handed to Mapbox (camera padding, `cameraFlight.ts`) is converted with `offsetWidth / rect.width`.
- **Inside the canvas**, viewport media queries and `vw`/`vh` measure the real screen, not the layout: use `@container rv-canvas (…)` and `var(--rv-canvas-width / --rv-canvas-height)`. Overlays portaled to `<body>` must either read the scale from their anchor (`readAppScale`) and position themselves with `appScaledOverlayStyle` (dropdown pattern; pass `inScaledLayer` when portaled into a scaled layer) or use `.rv-app-scaled-layer` (full-screen layers, `src/index.css`). A toolbar that may overflow a narrow column scrolls horizontally with edge fades (`useHorizontalScrollOverflow`) or wraps; it never clips controls.

### Themes (light / dark)
The settings' « Préférence d'affichage » (système / clair / sombre, `displayMode` in the project-browser settings) is resolved by `shared/lib/appTheme.ts` (`initAppTheme()` in `main.tsx` before the first render, `setAppThemePreference` from `SettingsPanel`, follows the OS while on « système ») into `<html data-rv-theme="light|dark">`; the default is « système ». Dark is the original theme and keeps its exact values; tokens live in `shared/styles/theme.css` (glass in `glass.css`, menus in `dropdown.css`). Colour rules in features: text, hairlines and translucent fills are the ink `rgb(var(--rv-ink) / α)` (white in dark, #111114 in light, same α), solid text `var(--rv-text)`; text/icons on the red or another solid colour `var(--rv-on-accent)` (white in both); a value specific to one theme is `light-dark(<light>, <dark>)` (`color-scheme` is set with the theme; `light-dark()` only takes colours, never a length or an alpha). Never write a literal white/black neutral in new UI. Light-theme design: white glass panels (0.9) with a soft `--rv-float-shadow` (never `none`: it composes with other shadows), raised elements white on a light-grey well (`--rvi-tl-card-surface`), status text in the dark tones (#b42318 / #b54708 / #067647), brand red and data colours unchanged. Map content (markers, their badges, route lines, labels) is identical in both themes; popups, menus, legends and cards follow the theme. White monochrome SVG icons must be masks painted with `currentColor`/`--rv-text` (`AssetIcon`, `SvgV2Icon`), not `<img>` (HTML-string popups darken theirs with a light-theme `filter: brightness(0)` rule); the logo goes through `RedViewLogo`. Canvas/WebGL/Stripe colours read `useAppTheme()` (chart slope outline, `stripeAppearance.ts`). The LiDAR viewer stays dark (it imports `theme.css` without initialising the theme).

### Client-side tile pipeline (Service Worker)
`public/sw-dem.js` is a thin entry that `importScripts()` modules under `public/sw-dem/{core,sources,processing,swiss,norway,spain,runtime,workers}`. It builds DEM, ortho, slope and altitude tiles in the browser from public sources (IGN, AWS Terrarium, swissALTI3D, Norway/Spain WCS); it returns 204 on real misses rather than synthesising flat tiles. DEM tiles are RGB PNGs with the Up filter compressed by the SW's own `zlibDeflateRle` (`core/terrain-rgb.js`; `CompressionStream` has no level and its level-6 match search is slow on noisy 0.40 m surfaces): 1.7-3.3× faster to encode and 10-36 % smaller than the former RGBA unfiltered tiles in Chromium, same elevations (`test/service-worker/sw-dem-png.test.ts`, `bench:dem-sw`). Contract: the page (`features/map3d/hooks/useMap/serviceWorker.ts`) registers the SW, waits for `controllerchange`, and only then adds `/dem-tiles/` and `/ortho-tiles/` sources. It reloads itself once only when a worker of another epoch served it at load (after a deploy): a first visit or a new tab already on the current worker is never reloaded (it used to be, losing the first seconds of map loading; `bench:dashboard -- --scenario sw`). **When you change anything under `public/sw-dem*`, bump the cache stamp in the header comment of `sw-dem.js`** so browsers see a byte diff and purge old caches. Analogous client cache invalidation for the app itself is `shared/lib/appCacheEpoch.ts` (`APP_CACHE_FIX_EPOCH` + build id from `VERCEL_GIT_COMMIT_SHA`/`GITHUB_SHA`).

On the Satellite basemap, `/vhr-tiles` (`sw-dem/sources/vhr-ortho.js`, attached by `useMap/controller/vhrOrtho.ts` right above the `mapbox.satellite` layer, z18–21, always 512 px tiles) overlays the IGN very-high-resolution orthos — `PCRS.LAMB93` 5 cm, then `THR.ORTHOIMAGERY.ORTHOPHOTOS` 5–10 cm — through WMS-R in EPSG:3857, and answers a transparent tile elsewhere so Mapbox shows (Mapbox Satellite in France is the IGN 20 cm ortho up to z19). `transformRequest` (`map3d/lib/satelliteTiles.ts`) also forces the `@2x` Mapbox Satellite tiles (GL JS only asks them at DPR ≥ 2, which the app's DPR cap rarely reaches): the terrain drape textures are 2× the screen, and 256 px tiles upscaled into them lost up to ~20 % sharpness at some zooms. The WMS paints no-data **pure white** (PNG is RGB-only, `TRANSPARENT`/`BGCOLOR` ignored): coverage comes from per-layer 64 px z14 masks, and border-connected white is cleared on the tile itself.

Slope and altitude overlays use `TERRAIN_ALIGNED_RASTER_TILE_SIZE` (`map3d/lib/sources.ts`) so Mapbox requests exactly the tiles of the terrain's DEM pyramid (`floor(zoom − 1)`); the SW then reads the DEM tile the 3D mesh already loaded. The altitude overlay goes further: outside an analysis zone it is a Mapbox custom source (`altitude/lib/altitude-dem-source.ts`) that re-encodes, in memory, the DEM tile the terrain already decoded (`tile.dem`) — no second download (as a raster source on the same URLs it queued behind the terrain and landed 1–2 s later), and it reloads a tile when the terrain replaces its DEM; only the zone-masked path still uses `/altitude-tiles`. A 256/512 px overlay would ask 1–3 zoom levels deeper and force the SW to build its own DEM pyramid (16–64× the IGN traffic). Slope tiles are never answered with a cancellation placeholder: a provisional tile (missing neighbour, stand-in DEM) is rebuilt when the DEM lands (`notifySlopeDemTileReady` → `SLOPE_TILES_STALE` → page reloads the source).

### i18n
UI strings are **the French/English source text itself**: components call `t('Texte français ou anglais')` (`useAppI18n`) or `translateAppText(...)`; translations are `{ fr: '...', en: '...' }` pairs in `src/shared/i18n/config/translations/*.ts`. `AppI18nProvider` additionally translates DOM text nodes and `aria-label`/`placeholder`/`title` attributes through a MutationObserver, so a new user-visible string needs a pair added or it won't translate. The API layer uses `api/_lib/translations-data.ts`, which is **generated** by `scripts/build/prebuild-api-i18n.mjs` (regex-extracts `{ fr: '…', en: '…' }` literals from every file of `translations/` except `index.ts`) — don't edit it by hand, and keep pairs as single-object literals with quoted strings (no template literals) so the regex still matches. One pair file per area (`global`, `dashboard`, `itinerary`, `lidar`, `map`, `app`, `auth`, `fitPredictor`, …); a new file must also be spread into `translations/index.ts`. On a duplicate key the later pair wins, but the locale's own keys always beat the other language's (a text already in the target language stays itself). The DOM translator only matches whole text nodes: a template literal (`` `${n} fichiers` ``) never translates — use `t('{{count}} fichiers', { count: n })`; canvas/WebGL/Mapbox text-field strings need `translateAppText` explicitly. The LiDAR viewer (`viewer.html`, no React) runs the same DOM observer (`shared/i18n/domTranslation.ts`) from `lidar/viewer/main.ts`. `npm run i18n:audit` (`scripts/quality/i18n-audit.mjs`, `--list` for details) reports coverage, missing strings, untranslatable template literals and conflicting pairs.

## Build/TS conventions
- Path alias `@/*` → `src/*` (tsconfig + Vite).
- `tsconfig.app.json` is strict with `noUnusedLocals`, `noUnusedParameters`, `verbatimModuleSyntax` (use `import type`), and `erasableSyntaxOnly` (no `enum`, namespaces, or constructor parameter properties).
- Env: browser-exposed vars are `VITE_*`; server-only secrets (Stripe, Appwrite API key, upstream URLs) are read from `process.env` in `api/`. `.env` is git-ignored — copy from `.env.example`.
- `.claudeignore` excludes `node_modules`, `dist`, `vendor/redviewalgo/target`, images/wasm and large geodata (`public/france-border.json`, POI icons, etc.).
