# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

RedView is a 3D route-planning / analysis app for ultra-cycling and bikepacking (React 19 + TypeScript + Vite SPA on Mapbox GL JS v3). It is French-first: root docs (`REDVIEW_*.md`, `STRUCTURE_REFACTOR_PLAN.md`), comments and commit scopes are largely in French/English mix. Commits follow conventional-commit style with a scope, e.g. `fix(chart,map): ...`.

## Commands

```bash
npm run dev          # prebuild API i18n data, then Vite dev server (also serves api/*.ts, auto-starts BRouter/POI, and opens an SSH tunnel to the VPS nginx when BROUTER/POI/WEATHER_UPSTREAM point at it — the VPS answers 403 to anything not local; see .env.example)
npm run build        # prebuild API i18n data + `tsc -b` + `vite build`  (type errors fail the build)
npm run check        # quality gate, in parallel: typecheck, lint, test, knip, cycles (~1 min cold, ~20 s warm)
npm run check:full   # + `vite build` + bundled prod servers started for real (server:check) + offline correctness regressions (bench:redview, project-layers, collab, flyover) — run by `npm run deploy` and CI
npm run test         # vitest run (test:watch = watch mode)
npm run lint         # eslint (flat config, TS/TSX + server.mjs/server/*.mjs), cached; lint:prune after fixing a frozen error
npm run knip         # unused files / dependencies / unresolved imports (blocking); unused exports/types reported only
npm run cycles       # madge: runtime import cycles in src (type-only and dynamic imports ignored) — must stay at zero
npm start            # tsx server.mjs — production server from sources: serves dist/ + api/*.ts on $PORT (default 3000); the images run the esbuild bundles instead (`npm run build:server` → dist-server/)
npm run services     # / services:stop — start/stop local BRouter (17777) and POI server (17778) manually
npm run bench        # full benchmark/regression suite (bench:quick = fewer iterations)
npm run bench:pente  # single suite; others: meteo, alti, neige, brouter, fit, lidar, poi, exporter, chart, server, flyover, follow, lidar-engines (viewer on WebGPU/WebGL 2 in Chromium + Firefox, after build:vite)
npm run lidar:index  # regenerate the Japan/NZ/Netherlands (AHN, GeoTiles)/Flanders (DHMV II, WFS) LiDAR file indexes + green coverage polygons for JP/NZ/NL/BE/France (IGN WFS)/Switzerland (STAC) (crawls cached in scripts/lidar-index/.cache, --refresh to re-crawl, --only=jp,nz,nl,be,fr,ch)
npm run workbench    # designer workbench: one self-contained HTML (scripts/design-workbench/out/) — black & white copy of the real dashboard captured from `npm run dev` (DOM + CSS, real layout modules bundled), text/spacing inspector, JSON export of the edits (rule, file:line, from → to); the capture clicks every tab/section/toggle/dropdown of the real app (3 levels, DOM patches + pop-in layers, restore verified) so a right-click in the workbench replays the app's click; ~2 min with 6 parallel headless browsers sharing one work queue (`--workers`, `--budget` seconds, Ctrl+C keeps what is captured); --skip-capture rebuilds from the cache; workbench:verify checks the overlay against the real app (4 screens) and the edit/export/import flow
npm run deploy       # alias `push` — see warning below
```

**Tests.** Unit tests are Vitest (`vitest.config.ts`, standalone: it must never import `vite.config.ts`, whose dev plugin loads `.env`, starts BRouter/POI and opens the SSH tunnel). They sit next to the module (`foo.ts` → `foo.test.ts`, explicit `import { describe, it, expect } from 'vitest'`), server ones in `server/__tests__/` and `api/_lib/__tests__/`; `.dockerignore` keeps them out of the image. Write them for pure business logic first (security boundaries, persistence, routing math, UI rules). The `script-test-bench/` benchmarks (run with `tsx`) stay for heavy/perf/real-data regressions, and `scripts/test-*.mjs` are ad-hoc probes against VPS services. Type-checking is `tsc -b`: app (`src`), `vite.config.ts`/`vitest.config.ts`, and `api/` + server tests (`tsconfig.api.json`, `allowJs` so `server/*.mjs` imports are typed).

**Lint ratchet.** Pre-existing ESLint errors are frozen in `eslint-suppressions.json` (ESLint bulk suppressions): any new error fails `npm run lint`; after fixing a frozen one, `npm run lint:prune` (the gate fails on stale suppressions too). `_`-prefixed names are intentionally unused (same rule as tsc's `noUnusedParameters`). Never add a suppression to get a change through: fix the error.

`npm run deploy` first runs the quality gate (`scripts/check.mjs --full`) on the working tree; on failure nothing is committed or pushed (`--skip-checks` exists for emergencies only and leaves a `Checks-Skipped: true` trailer). It then runs `git add .`, commits, pushes to `origin/main`, and triggers the Coolify deploy over SSH to the production VPS. Never run it unprompted. CI (`.github/workflows/ci.yml`) runs the same `check:full` on every push and PR to `main`.

### Rust/WASM prediction engine

`vendor/redviewalgo/` is a Rust crate: the cycling moving-time engine v2 (`src/cycling/`: physics + behaviour simulated on a ~10 m grid — power policy by gradient, descent comfort speed, corner radius √(a_lat·R) with braking/re-acceleration, surface, walking, warm-up/endurance; level presets in `cycling/presets.rs`; FIT calibration with built-in cross-validation in `cycling/calibrate/`), the running engine (`src/running/`, KNN), FIT/GPX parsing. The cycling engine returns **moving time only and takes no pauses** — pauses belong to the app's schedule (`pauseAwareSchedule`). Bump `ENGINE_VERSION` (`cycling/mod.rs`) and `CYCLING_ENGINE_VERSION` (`fitPredictor/engine/version.ts`) together when results change: older persisted bike predictions are recomputed.

Rebuild with `powershell -File vendor/redviewalgo/build.ps1` (no wasm-pack needed): it calls the rustup toolchain directly, checks the wasm-bindgen CLI version against `Cargo.lock`, runs the unit tests on wasm32 under Node (`wasm-bindgen-test-runner`; in test modules shadow `#[test]` with `wasm_bindgen_test` under `cfg(target_arch = "wasm32")`, native tests can't link on windows-gnu), then writes the JS glue + `.wasm` into `src/features/fitPredictor/engine/pkg/` and copies `redviewalgo_bg.wasm` into `public/`. `-OutDir <dir>` builds elsewhere without touching the app; `-SkipTests` skips tests. Both outputs are committed; `target/` is ignored. The frontend talks to it only through a Web Worker (`fitPredictor/engine/api.ts` → `worker.ts`; bike path in `itineraryPanel/hooks/useItineraryFitRuntime/cycling.ts`).

Accuracy bench: `npm run bench:pace` (`script-test-bench/pace-accuracy/`, real Chamonix→Paris FIT rides + synthetic physics scenarios, non-zero exit on a hard-criterion failure); `npm run bench:pace:prep` fetches OSM tags (prod BRouter proxy) and historical wind once into a git-ignored cache; `npm run bench:pace:realism` compares famous climbs (BRouter geometry, IGN elevation), flat speeds and GT20 against public references. FIT files are not in the repo (`PACE_FIT_DIR`).

Routing bench: `npm run bench:routing -- --label <name>` (`script-test-bench/routing-quality/`) runs ~660 scenarios (9 bike presets + variants + running/trail, 15–1 200 km) through the real client + `api/brouter.ts` pipeline against prod BRouter, which needs an SSH tunnel (`ssh -i ~/.ssh/oracle_brouter.key -N -L 27777:127.0.0.1:17777 opc@141.145.220.99`; nginx `/brouter` is closed to the public). It stays sequential (`--concurrency` ≤ 2) to keep prod's 4 BRouter threads free, and resumes an interrupted run. `bench:routing:sweep` calibrates the A* coefficient, `bench:routing:compare -- --before a --after b` writes `reports/routing-quality/ROUTING_QUALITY_REPORT.md` with guard-rails (non-zero exit on failure), `bench:routing:report` the HTML page. Latency through the tunnel depends on the client's line: for faithful numbers build `routing-quality/vps/build-vps.mjs` (single-file bundle, Node ≥ 20) and run it on the VPS next to BRouter.

## Architecture

### Four deployable pieces
1. **Frontend SPA** (`src/`) — two Vite HTML entries: `index.html` (app) and `viewer.html` (served at `/viewer`).
2. **Node "serverless-style" API + static server** — `api/*.ts` are Vercel-style handlers (`(req, res)` with `req.query`, `req.body`, `res.status().json()`). They are executed by **two separate adapters that must stay in sync**: the `redviewDevApiPlugin` in `vite.config.ts` (dev, via `ssrLoadModule`) and `server.mjs` (prod, Docker/Coolify, `node:22-alpine`, `Dockerfile`). In the image, `server.mjs` and every route are bundled by esbuild into `dist-server/` and run by plain `node`, no tsx (`scripts/build-server.mjs`: routes as `dist-server/api/<route>.mjs`, `process.env.REDVIEW_SERVER_BUNDLE` defined at build time; only package.json `dependencies` stay external and are installed in the image — browser-only packages are `devDependencies`, and a bundled devDependency fails the build). Static files are precompressed at build (`scripts/precompress-dist.mjs`, rule in `server/static-compression.mjs`): `server.mjs` serves the `.br`/`.gz` variants by negotiation and never compresses at runtime when they exist. Every server in-memory cache is bounded in bytes with `server/byte-lru.mjs` (containers have memory limits) — a new cache must use it. Both map `/api/<name>` → `api/<name>.ts`, collapse `/api/openmeteo/*` and `/api/weather/*` (server.mjs also `/api/brouter/*`) onto one file, and both re-implement the `/radar-tiles`, `/slope-tiles`, `/altitude-tiles`, `/dem-tiles` fallbacks using `server/radar-recolor.mjs` and `server/terrain-tiles.mjs`. A new API route shape or tile route usually needs changes in both places. Path normalisation, `/api` route resolution (no `_lib/`, no encoded `..`), body-size limits (`bodyLimitFor`), client-IP/rate-limit keys, tile-coordinate validation, the radar host allowlist and the `/api/pointcloud` upstream allowlist (LiDAR sources without CORS: AHN sub-tiles from GeoTiles, DHMV II strips from EODaS OpenLidar — streamed with `Range`, never buffered) live in the shared `server/http-security.mjs`, used by both adapters — change them there, not in each adapter. `server.mjs` also owns in-memory rate limiting, security headers and the CSP (`REDVIEW_CSP_HEADER`) — **any new external host the browser talks to (tile servers, APIs) must be added to that CSP**.
   **Observability** (prod adapter only; the dev plugin has none on purpose). Errors go to self-hosted **GlitchTip** (`errors.redview.tech`, Sentry protocol — not Sentry). Front: `@sentry/react` in `src/main.tsx`, release = build id. The build id has one source, `server/build-id.mjs` (Vite define, sourcemap tag, server release). Sourcemaps are built `hidden`; the Docker builder runs `scripts/upload-sourcemaps.mjs`, which uses `glitchtip-cli` (pinned SHA-256; sentry-cli's chunked upload does not work with GlitchTip) to inject debug IDs into `dist/assets` only (never the `public/` SW scripts), upload the maps, then delete every `.map`. `server.mjs` also 404s any `.map`. Server: `server/observability.mjs` (`@sentry/node`, only with `SENTRY_DSN_SERVER`, errors only, tags route/request id/method set in a local `withScope`, scrubbed of headers/query/body/IP, flushed on SIGTERM) and `server/request-logging.mjs` (pino-http: one JSON line per request on stdout with method, **normalised** route (`normalizeRoutePath`, which the server sets on `req.redviewRoute`), status, duration, `X-Request-ID` (a safe incoming one is kept, otherwise a UUID; echoed in the response and exposed to handlers as `req.requestId`) and build id; never the raw URL, query or headers; a 2xx `/health` is silent, static assets log at debug, `LOG_LEVEL`). `api/poi.ts` forwards `X-Request-ID` to the POI server, whose Fastify logger writes the same line shape (`server/poi-server/server.js`).
3. **Real-time co-editing server** (`server/multiplayer/`, Coolify service `redview-multiplayer` built from `Dockerfile.multiplayer` — the image runs the esbuild bundle `dist-server/multiplayer.mjs`, collab engine from `src/` included —, deployed by `npm run deploy` before the app): its port is published on `127.0.0.1:17790` only, and the **host nginx** (`/etc/nginx/conf.d/app.conf`, which also proxies the app to `127.0.0.1:3000`) routes `/multiplayer` to it with WebSocket headers — public traffic never goes through Coolify's Traefik labels. The app shows « Partager » only when `/multiplayer/health` answers `{"ok":true}` (that is all it answers; an unknown path returns the SPA's `index.html` with 200). Metrics (rooms, clients, journal/checkpoint latency, errors, shadow validation, event-loop delay, heap) are served on the container's internal port 17791 only, never proxied: `sudo docker exec $(sudo docker ps -q -f name=krejrvgvs2w5kmfo27rutffz) wget -qO- http://127.0.0.1:17791/metrics.json` (`/metrics` = Prometheus text). Errors go to GlitchTip when `SENTRY_DSN_SERVER` is set on that service (same `server/observability.mjs`). See `features/collab` below.
4. **VPS microservices** (Oracle VPS behind nginx, reached through the `api/` proxies via `BROUTER_UPSTREAM`, `POI_UPSTREAM`, `WEATHER_UPSTREAM` — see `.env.example`):
   - BRouter standalone (port 17777) — routing engine; `api/brouter.ts` whitelists query params and uploads dynamic BRF profiles. In dev, `scripts/start-dev-services.mjs` starts a local one if a sibling `../redview-brouter` checkout exists. The frontend generates a fresh ~500-line BRF profile from UI sliders on each change (`brf-template.ts`); see `REDVIEW_ROUTING_ARCHITECTURE.md`. Search is always single-pass (`pass2coefficient=-1`); the A* `pass1coefficient` is set per request from the profile's cost per metre (estimated in `brf-template/values.ts`, then learned from responses) and the distance (`lib/brouter/api/searchCoefficient.ts`, bounded server-side by `api/_lib/brouter-search.ts` — same distance steps on both sides, enforced by `searchCoefficient.test.ts`). Every itinerary is routed with its generated profile, even with neutral sliders — never a stock BRouter profile (`routing-resolver.ts`; an upload failure is retried once, then reported). Sections longer than ~180 km are routed coarse first, then refined between anchors placed on the coarse track (`routing/long-distance-anchors.ts`, orchestrated in `useItineraryBrouterRouting/resolveRouteRequest.ts`); a slow fine search is hedged by a greedier one after a distance-based delay (`customProfileFetch.ts`), and when it still times out the same anchor method runs with tighter anchors (then a greedier coarse search) instead of any fallback profile. Timeouts stop at response headers, not download. Local edits (move/insert/remove a point, forbidden zone, on BRouter or imported GPX routes alike) only reroute a ±80 km window of the stored route around the edit (`narrowRoutePatchToEdit`, `routeSegments.ts`); patch bounds taken on the route carry their `distanceM`. **A stored route never contains a straight line** (they end up in the GPX export): every join of route pieces (patch, extension, request legs, recalculation, merge) must meet within `ROUTE_SEAM_TOLERANCE_M` (`lib/routes/route-continuity.ts`); a patch's intermediate bounds are requested on the stored track (`anchorRoutePatchBound`) and spliced where the routed piece really rejoins it (`planRouteSplice`), a `start`/`end` bound replaces everything before/after it, and a join that fails widens the window then falls back to a full recompute (`RouteSeamError`), never a line. Start/finish placed on the route crops it without routing (`cropRoutePoints`, `placeRouteEndpoint`); the LiDAR viewer's freehand gestures on a routed itinerary are translated into the same app edits (`lidarViewerRouteEdit.ts`); GPX segment jumps and sparse `<rte>` files are routed at import (`importedGpxGaps.ts`); old start/end artifacts are dropped on normalisation (`repair-route-endpoints.ts`). Checks: `npx tsx script-test-bench/route-continuity/run.ts` (prod BRouter through a tunnel) and `node script-test-bench/route-continuity/e2e.mjs` (needs `npm run dev`). `api/brouter.ts` compresses route GeoJSON (brotli/gzip) since `server.mjs` only compresses static files.
   - `server/poi-server/` — Fastify + SQLite/R*Tree POI server (port 17778), built by `server/poi-ingest/`.
   - `server/weather-daemon/` — Python GRIB ingest + tile server (systemd units, nginx conf).
   - Host configuration (BRouter unit and its 3 GB heap, systemd resource drop-ins, sysctl, journald, Docker `daemon.json`, Appwrite compose override) is versioned in `server/vps/` — its README gives where each file goes, how to apply/roll back, and the **Always Free memory floor** (Oracle reclaims an idle A1 instance when CPU, network *and* memory stay under 20 % for 7 days; memory is the only one above: keep used RAM ≥ 25 %). `bash scripts/vps-perf-snapshot.sh <label>` takes a read-only before/after snapshot.

### Frontend structure (`src/`)
- `App.tsx` handles bootstrap: Appwrite session, subscription gating (currently all registered users get access during open beta; non-subscribers are labelled `demo`), mobile block, then lazy-loads `pages/Dashboard`. **Initial load:** `index.html` paints a static splash (`.rv-boot`, inline styles, OS theme until `data-rv-theme` is set) that `BootstrapScreen` re-renders identically, so there is no white page. The Dashboard shell (project browser) loads without the 3D editor: `DashboardEditor` is `lazy()` (`pages/Dashboard/editorLoader.ts`), prefetched when the browser is idle, when a project card is hovered (`data-rv-project-card`) and as soon as a project starts opening. The shell must import concrete modules, never the `map3d`/`controlPanel` barrels, and the LiDAR provider only holds a slot (`lidarManagerSlot.ts`: the `LidarManager` is created by `useLidarManager()` in the editor and destroyed with the Dashboard). `npm run bundle:check` (part of `check:full`) fails if mapbox-gl, mapbox-gl-draw, copc, proj4 or the editor land on that critical path, or if it exceeds 300 KiB brotli (271 KiB measured, 1 075 KiB before the split).
- `pages/Dashboard` is the composition root: it owns the Mapbox instance, active project state, and wires the feature panels together. Project persistence goes through `shared/utils/projects/*` (Appwrite rows + compression + IndexedDB cache in `shared/utils/storage`). A gzip payload over ~12 M chars (nginx limit in front of Appwrite) goes to the `project-payloads` bucket instead (`payloadFiles.ts`, chunked upload, ≤ 30 MB ≈ 100 MB of project) and the row's `data` holds `file:<fileId>`; any code reading `projects.data` must handle that pointer. Note: older docs mention Supabase; the live backend is **Appwrite** (`shared/services/appwrite.ts`, `node-appwrite` server-side in `api/_lib`).
- **Server state & toasts.** Server state (Appwrite lists, account, billing, API) goes through TanStack Query (`shared/services/queryClient.ts`: 30 s stale, no 4xx retry, failed mutations toast unless `meta.silentError`; cache cleared on every session change in `App.tsx`), one `queries/` folder per feature (first: `projectBrowser/queries/projectLibrary.ts`, cache updates as pure functions). Never for the editor document (ProjectStore/autosave) or the map. User feedback toasts only through `notify` (`shared/ui/notify.ts`, sonner rendered unstyled by `AppToaster`).
- `features/*` are feature-sliced domains (`altitude`, `slope`, `snow`, `weather`, `sunlight`, `lidar`, `poi`, `fitPredictor`, `map3d`, `centerPanel`, `controlPanel`, `itineraryPanel`, `projectBrowser`, …). Convention (see `STRUCTURE_REFACTOR_PLAN.md`): `index.ts` is the public API, plus `components/ hooks/ lib/ types.ts`; import a feature through its `index.ts` where one exists — except from a module that this barrel re-exports, directly or transitively (low-level contexts, markers, map helpers): import the concrete module there, or the barrel closes an import cycle (`npm run cycles` fails). Not every feature is fully migrated to this shape. `shared/` holds cross-cutting components, hooks, i18n, services, utils. `features/freeCam` is the game-style free camera on the 3D map (F, ZQSD/WASD, Shift/Ctrl, mouse look under pointer lock, wheel = speed multiplier): speed scales with the height above ground, and a velocity (`lib/velocity.ts`, frame-rate independent exponential response: ~0.4 s to full speed, ~1 s glide on release, hard stop under 1 % of the speed) drives the pose; at rest the map is never touched.
- The central domain object is `ItineraryProject` (1..N route variants plus rider config, map viewport and per-panel settings). It is the *composed* form the UI works on; it splits into three layers (`itineraryPanel/lib/project/layers.ts`, the single source of truth, groundwork for real-time co-editing): the **document** shared by every editor (name, itineraries, copies of the custom routing profiles they reference — `toProjectDocument`, stored in `projects.data` as `{ schema: 2, … }`), the per-user **view** (`PROJECT_VIEW_KEYS` + `ITINERARY_VIEW_KEYS`: active itinerary/mode, timeline view, `controlPanel`, `analysis`, `dashboard`, each itinerary's eye/render mode/opacity — stored apart in IndexedDB `views` + the Appwrite `project_views` collection, one doc per (project, user), last write wins, `projectViews.ts`) and the per-device **local work** (`ITINERARY_LOCAL_WORK_KEYS`: `pendingRoutePatch`, `pendingTraceExtension`, `pendingFitRecompute` — only in the IndexedDB copy's `work_json`, never in the cloud: the device that made an edit computes its result). A new field belongs to the document by default; a display state must be added to the view keys. The Dashboard sorts each change with `classifyProjectChange`: a view-only change never serialises or rewrites the project (no version, no multi-device conflict); `saveProject` skips a document the cloud already confirmed. Undo/redo never touches the view. Older stored projects (composed, view and work inside) stay readable everywhere (`readStoredProject`/`storedProject.ts`); on first open their view seeds the user's stored view (create-only, timestamped at the project's last save). Document item ids come from `createDocumentId(prefix)` (time + random: unique across editors). Custom routing profiles are the account's library (`prefs.routingProfiles`, local mirror `redview:routing-profiles:v2` with pending upserts/deletes replayed over the account copy; legacy `redview_custom_routing_profiles` adopted once); the selector also lists the project's embedded copies. `npm run bench:project-layers` checks the layers; `script-test-bench/audit/a-persistence-sim.ts` runs the real persistence code on a mocked Appwrite/IndexedDB (scenarios V1–V6, PR1 cover views, migration, local work, missing collection, profiles). `scripts/setup-appwrite-schema.mjs --only=project_views` creates the collection (without it views stay local, logged once).
- `features/collab` is real-time co-editing of the document layer, Figma's model: the server is authoritative (plain-language overview, rules for changes, tests: `REDVIEW_COLLAB_TEMPS_REEL.txt`). The document is flattened into objects with properties (`collab/model/`: ids derived from the document — root `p`, itineraries `p/itineraries:<id>`, list items `<parent>/<field>:<key>`; settings one property per key, lists one object per item at a fractional index (`fractional-indexing`, ties re-positioned by the server), routes as a header property + content-addressed chunks, `routeChunks.ts`; merge rules in `collab/schema.ts`). Ops are `c`/`d`/`s`/`m` (create, delete with descendants, set = last writer wins per property, move); `diffDocument` compares by reference (`toItineraryDocument` is memoised per itinerary so unchanged ones are skipped), `invertOps`/`applyOpsWithInverse` give exact inverses, `Materializer` rebuilds only replaced objects and `adopt()` hands the app back its own objects. The ProjectStore only knows the `ProjectCollabLink` contract (`ProjectStore/collab.ts`): with a link every committed document is pushed (`user`/`step` = the user's actions, `background` = async results, `comment` = comments: never an undo step, sent even before `welcome`), other editors' documents are recomposed with this device's view and local work (`externalRevision` bumps). **Nothing typed while connecting is lost**: `useCollabSession` hands the link over as soon as the session exists (`pending` while its module loads: the store records its writes and uses `SESSION_PENDING_COMPUTE_GATE`, no stale computation), the store calls `bind(base, changes)` — the document it showed (cloud checkpoint, or the fresher local copy: `getProject` picks it for shared projects) becomes the client's *provisional* confirmed state, its writes since are replayed exactly — and only then the WebSocket opens; until the first `welcome` the user's edits are ordinary pending batches, replayed on the server snapshot then sent, while `background` results computed on the provisional base stay local (`localOnly`, dropped at `welcome`: they would overwrite the session's). Unsynced batches (pending + acked-not-durable) are also kept on the device (`client/unsyncedStore.ts`, IndexedDB `redview-collab`, written ≤ 250 ms after a change and on `pagehide`) with their `clientId`; the next session of the same user on that project adopts them under a Web Lock (one tab only; no Web Locks → nothing kept) and resends them, `welcome.clientSeq` deduping (`client/session.ts`). Header: `data-rv-collab-status` (`connecting`/`online`/`offline`) on `.rvi-header`, a status line only if it lasts (> 1.2 s / 2 s); a refusal (4404 project deleted, 4403 access removed) toasts and returns to the project browser and drops the device copy. Client (`collab/client/`): `SyncEngine` (confirmed state at seq N + pending batches; visible = confirmed + pending replayed, so a remote value on a property you just changed is masked until your ack; own batches kept until `durable` and resent after a server crash, `welcome.clientSeq` says which ones the server has), `UndoHistory` (per user, client-side inverses; never restores a property someone else changed since; deletions recreated with all properties; a background result joins the step of the action that caused it, so undoing a waypoint move restores the old route without routing), `LeaseGate` (`DerivedComputeGate` by server leases: the author of the last change to the inputs (`DERIVED_INPUTS`) has priority for 5 s, then the first requester; `beginCompute` claims the lease, the release is sent after the result batch; offline > 4 s → computes alone), `CollabClient` (transport-agnostic) and `CollabConnection` (WebSocket, ~30 Hz batches, backoff + jitter, 1012 = quick reconnect, 4403/4404/4426 = denied). Room core without I/O (`collab/room/`: `RoomState` orders, validates (`model/validate.ts`, with the comment author rules of `model/commentRules.ts`) and dedupes batches, `Room` handles messages, catch-up per `epoch`, leases, presence, and relays the ephemeral `motion` channel of `features/livePresence` — `room/motion.ts`: sanitised, 40/s token bucket per client (excess dropped, never a close), merged last state given in `welcome.motions`, sent to everyone but the sender as `volatile` (skipped by the server above 256 KB buffered instead of queued), never journaled). - LiDAR rendering (`lidar/viewer`): tiles stream as additive octrees from the OPFS LOD cache (`lib/lodCache.ts` v2, 16 B/point: position, class, intensity, RGB and the cell-filtered RGB/intensity a node shows where none of its children is drawn, so coarse levels look like a mip level instead of salt-and-pepper samples; a v1 cache is upgraded on open, no decoding). `SceneLod` selects nodes by projected spacing under the adaptive moving budget (`lodBudget.ts`); once the camera stops, `lod/restRefinement.ts` grows the budget towards ~50 ms of GPU per still frame (platform `restMaxBudget`), then accumulates 16 sub-pixel-jittered frames in linear light (`renderScene({ accumulate })`) and idles. - **Two rendering backends, one viewer** (Linux compatibility). The viewer only talks to the `LidarRenderer` interface (`viewer/renderer/sceneRenderer.ts`), implemented by `WebGpuLidarRenderer` (`viewer/renderer.ts`) and `WebGlLidarRenderer` (`viewer/renderer/webgl/`), each a lazy chunk loaded only when chosen. **Never read a WebGPU global (`GPUShaderStage`, `GPUBufferUsage`…) at module level**: Firefox on Linux has none, and one such constant made the whole viewer throw on import there (`noWebGpuApi.test.ts` imports every renderer module without them). Both draw the same frame: lazy per-node shading (WebGL 2: the WGSL compute pass as a vertex shader captured by transform feedback), instanced sprites with the adaptive size, chunked terrain LOD, overlays, route/analysis meshes, sun trajectory, EDL, reduced resolution while moving, MSAA on discrete GPUs, rgba16f accumulation (needs `EXT_color_buffer_float`, else still frames are not averaged) — so tools, comments, route editing, look-around and snow run on both. `createLidarRenderer` (`renderer/createRenderer.ts`) takes WebGPU when the preflight (`renderer/device.ts`: 8 s adapter / 10 s device timeouts — some Linux Vulkan stacks never answer; fallback and software adapters refused) finds a hardware adapter, else WebGL 2 on a fresh canvas (`renderer/canvas.ts` `claimViewerCanvas`: a canvas keeps its first context type). That is the usual Linux path in 2026: Firefox ships WebGPU on Windows/macOS only, Chrome enables it on Linux for Intel Gen12+ and NVIDIA on Wayland. The GLSL in `webgl/glShaders.ts` is a line-for-line port of the WGSL sharing the std140 `Scene` block (`packSceneUniforms` fills both): **a shading/overlay change goes into both**. WebGL has no clip control in Firefox, so its depth is conventional with the camera's near/far (`camera.getDepthRange()` → `setDepthRange`, linearised by its EDL pass). `?engine=`: absent = auto, `webgl` = WebGL 2, `terrain` = the older textured DTM without points (`viewer-webgl/`), also the last resort when neither backend starts; two GPU context losses within 2 min step WebGPU → WebGL 2 → terrain. The panel's « Moteur » lists the three (WebGPU greyed out with the reason when unavailable). WebGL renderer strings (ANGLE, Mesa, Firefox's sanitised names) map to the same GPU tiers (`resolveWebglPlatformInfo`); CPU rasterisers (llvmpipe, SwiftShader, WARP) get the `software` profile. Without GPU timers (Firefox never exposes them) still frames are judged on the real interval (`FrameClock.lastIntervalMs`, long frames included) and a complete still frame over 200 ms ends the refinement (`restRefinement.ts`). Input is platform-neutral: the tools menu opens on the right-button release and `contextmenu` is always cancelled (Linux sends it on the press), wheel deltas are normalised (`wheelDeltaPixels`: Firefox reports lines). `npm run bench:lidar-engines` (Playwright Chromium + Firefox, synthetic LAS tile, external network cut; CI job `viewer-linux` on Ubuntu with `--expect-auto webgl`) checks render, EDL, colour modes, terrain, slopes, sunlight, right click in Linux order, drag-pan, line-mode wheel and `gl.getError()`; `bench:lidar-shots -- --params engine=webgl` compares both backends on a real tile (2026-10-06, tile 0965_6500: mean difference ≤ 0.21/255, same LOD selection).
- `features/snow` is the snow depth of the LiDAR viewers' snow modes (WebGPU and WebGL; heights come relative to the scene centre, hence `altitudeOffsetM`). `runSnowPipeline` loads in parallel the AROME 0.01° analysis (`/api/meteofrance`, ±0.4° × 0.3°; outside the AROME domain an Open-Meteo coarse grid), `/api/snow-context` (flat-field station depths: SLF IMIS and the Météo-France open hourly `NEIGETOT` of the surrounding départements, streamed and cached server-side, buddy-checked; the BRA snow cover through DPBRA with `METEOFRANCE_API_KEY`, massif outlines in `api/_lib/snow/braMassifs.ts`; 60 days of Open-Meteo weather) and Terrarium tiles (model orography of every cell, ±7 km far-field DEM); the viewer adds the canopy read from the point cloud. The engine (`lib/engine/`, pure functions, runs in `lib/engineWorker.ts` and under Node) learns the snow–elevation profile from the cells against their orography, corrects it as k·background(z + Δz) on the stations/BRA then optimal interpolation (ECMWF structure functions, leave-one-out diagnostics), redistributes the accumulation by the wind (drift flux divergence blended with Winstral exposure, rose and thresholds from the weather history), gravity (SnowSlide, CHM holding curve read at a 30 m slope, Gruber deposition, α = 30° energy line, deposits slump to 24°) and forest (Varhola), melts it by exposure (Hock melt index with horizons, scaled on the BRA north/south depths) and caps the wind amplitude with Helbig's σ. Every default carries its reference in `lib/engine/config.ts`. `npm run bench:snow` runs the physics checks and synthetic worlds (reference model written in the bench) against the frozen v1 engine (`script-test-bench/snow-quality/legacy/`), non-zero exit on a regression; `bench:snow:image` draws the before/after plate (real IGN LiDAR HD relief + synthetic world).
- `centerPanel/flyover` is the 3D route playback (toolbar Play). `FlyoverController` runs outside React: on Play it builds a camera rail once (`engine/cameraRail.ts`, pure functions, cached per route and prebuilt on idle) — route resampled at constant spacing, playback speed curve (time spread by tortuosity and grade at the camera's scale, capped heading rate, bounded relative acceleration, global factor solved for the target duration `22 s·√(L/10 km)`), camera distance tied to speed (constant on-screen flow; it follows the speed smoothed over 2.5 s and slew-limited to 6 %/s of zoom, `framingSpeedMps` — the raw speed dips at every sharp bend and made the camera dive and climb back within a second), zero-phase smoothed centerline/heading (heading smoothing divided by straightness²: hairpins follow the climb axis, laps and U-turns don't spin the camera), relief pitch, and a helicopter weight (tortuous climbs such as Alpe d'Huez: slow orbit on a small arc around the target, a bit higher and steeper; the heading limiter reserves the orbit's rate). A rAF loop then does O(1) work per frame: `PlaybackTransport` (ease-in, pause deceleration, exact arrival braking, speed spring), FreeCamera pose (`setFreeCameraOptions`, pitch/bearing from the eye→target vector), terrain guard (`queryTerrainElevation` along the sight line, asymmetric lift), head DOM marker and trail via `line-trim-offset` on a source set once (never `setData` per frame). While it drives the camera, `map/cameraDriver.ts` batches the camera events like a Mapbox animation (one *start, `move`/`zoom`/`rotate`/`pitch` per frame, one *end on release): per-frame `moveend` would clear the terrain line render cache, force `MapBlurMirror` copies and save the viewport. Approach/seek/resume use `flyTo` (works from the globe) then a FreeCamera handoff; the end flies to a whole-route overview. Playback widens the vertical FOV to 44° through the private `map.transform.fov` (`map/fov.ts`, animated during the approach, restored on close) and moves the camera closer by the same ratio (same framing and tile LOD). A session shows the route alone: POI layers suppressed (`setPoiLayersSuppressed`), every other map marker and popup hidden by `[data-rv-flyover-session]` (`src/index.css`) except the head (`data-rv-flyover-head`); re-asserted every second and after a style reload. Map interactions are suspended and `map3d/lib/cameraOwnership` is set while it owns the camera (idle rotation and the context menu step aside). React reads a status store (≤ 4 Hz) and a chart-cursor store (≤ 30 Hz, only `AnalysisChartWithFlyoverCursor` re-renders); chart/trace clicks seek while a session is open. Tuning lives in `flyover/config.ts`; `npm run bench:flyover` simulates playback at 30/60/144 fps on synthetic and real (Alpe d'Huez, Galibier) routes and fails on heading rate/acceleration, framing, duration or frame-rate dependence regressions.
- `centerPanel/flyover/video` is the flyover's MP4 export (Exporter panel « Vidéo flyover »: 16:9 1920×1080 or 9:16 1080×1920, 30 fps H.264 through WebCodecs + `mediabunny`, written into Blob chunks, downloaded at the end; the job lives in `exportStore.ts`, outside React). Never a screen capture: `VideoMap` builds an offscreen Mapbox map from the live style (`getStyle()`; custom sources re-created through their `cloneForMap()`, POI/hover sources dropped, raster fades and style transitions at 0, DEM URLs re-tagged `rv-src=video` so the SW never prunes their LiDAR work for the live map's `DEM_WANTED_TILES`), sized to the video and rendered at 2× then downsampled (`withDevicePixelRatio` scopes the page-global DPR to its own renders, construction and tile requests; `@2x` sprite forced by its `transformRequest`). Its rAF is cut (`_triggerFrame` only flags): the export loop renders a frame until Mapbox fires `idle` inside that render (every tile, source and label), never re-rendering while tiles are still missing; the Mapbox clock is pinned during a render and pushed 1 s per render (always ahead of real tile timestamps, fades done next render) and the average elevation (fog/horizon) is applied at once instead of eased (its easing cost a second 4K render per moving frame). After one frame times out (25 s), the next ones wait 3 s until one completes. It reloads the slope/altitude tiles the SW reports stale, like `listeners.ts` — never DEM tiles in place (`_reloadTile` on a terrain tile could stay `reloading` forever). `FlyoverVideoDirector` is the deterministic montage (whole-route overview → van Wijk approach → rail with the controller's laws at the toolbar's speed step + a framing pull-back pre-computed on the rail (`framingScaleProfile`: playback simulated once, pull-back the head needs to stay in frame, ±4 s running max then 1.5 s smoothing — it starts before a U-turn and holds through a hairpin section; a reactive guard pumped in and out) → arrival → overview); a scout director a few seconds ahead preloads the next tiles into each source's tile cache (Mapbox `_preloadTiles` with every loaded tile adopted by `_cache` instead of discarded — discarded, its GPU texture leaked; DEM borders re-backfilled when such a tile is restored), ≤ 16 tiles per source per call and only into a source with nothing pending for the current frame (S3 terrarium is HTTP/1.1: 6 connections, a preload queued ahead of an on-screen tile cost 5× the render time); `fetch` warm-up as fallback. Before frame 0 (« Préparation »), every tile of the first 4 s (overview + approach, ten zoom levels in two seconds) is fetched into the HTTP/SW caches, bounded at 45 s. No live preview: the loop only renders, captures and encodes. The end-of-export console line (`[flyover-video] … i/s : N rendus …`) gives renders per frame and the sources frames waited on. Portrait has its own framing (`engine/framing.ts`: 60° vertical FOV, longer target lead, centerline held closer). `npm run bench:flyover` checks the portrait framing and the montage (announced frame count, continuity across cuts).
- Route lines (trace, casing, surface patterns, selection, flyover trail) are elevated with `line-elevation-reference: ground` + a small clearance (`itineraryPanel/lib/route-layer/routeElevation.ts`): Mapbox then reads, per tile, the DEM tile the mesh is drawn with. Never an absolute (`sea`) height profile from the route altitudes: bare-earth altitudes sank under the HD surface model and hid up to half the visible trace, depending on the zoom level. Below zoom 6.5 (globe, where Mapbox skips elevated lines) they are draped; the switch follows `zoom`, not `zoomend`.
- `features/map3d` wraps Mapbox (terrain, custom WebGL layers, `hooks/useMap/*`). The map saves its viewport 500 ms after `moveend`; that value comes back as `initialViewport` and `useMap` ignores its own echo (only another viewport is jumped to) — it used to snap back any camera flight started within those 500 ms. Heavy compute lives in Web Workers / WASM (LiDAR `.las/.laz` via `copc` + `laz-perf.wasm`, FIT prediction). **`styledata` handlers must be idempotent** (touch the style only when something is missing or different): every `styledata` flushes Mapbox's terrain drape cache (all proxy tiles re-rendered), and a handler that mutates unconditionally re-fires `styledata` on the next frame — `moveLayer` dirties the style even for a no-op move, so `useLidarSelection` restacking on each `styledata` kept the map re-styling every frame, never idle. `TerrainManager.init()` only calls `setTerrain` when source/exaggeration differ (the anti-flat guards call it on every `styledata`/idle/heartbeat). The style bootstrap (`hooks/useMap/controller`) mutates the style once Mapbox parsed it (`canMutateStyle`), never on `isStyleLoaded()` (which also waits for the sprite, TileJSONs and imports), and waits for that parse without a deadline; every watchdog judging Mapbox's progress (stuck style, force-3d, heartbeat, loading deadline, reload verify…) runs on `controller/visibleClock.ts`, never a wall-clock timer: a hidden page (background tab, minimised or covered window — Vite reloads it there when another session edits a file) gets no animation frame, so Mapbox parses no style (`Style#loadJSON` waits for one), loads no tile and never goes idle.

### Typography & UI density
- **Type scale**: every text size goes through `src/shared/styles/typography.css` (`--rv-font-size-2xs…4xl`, `--rv-font-sans`), whose header holds the role table (panel title 16/600, section/tab 14/600, label 13/500 dimmed, control value/button/menu 13/600, compact toolbars and dense 2-column grids 12/500, caption 11, …). Never write a literal `font-size` or a fluid one (`vw`, `cqi`, `clamp`) in a feature; pick the role's token. Canvas/sprite text uses `RV_FONT_SANS` (`shared/lib/typography.ts`). Rethink Sans is the only font.
- **Density**: the dashboard is rendered on a logical canvas scaled by `appScale` (`shared/lib/appScale.ts`). Rule: **never below 1:1 on a standard-density screen** — a CSS px already carries the OS scaling and browser zoom, and shrinking gave blurry 8–10 px text on non-HiDPI screens (half-screen 1080p, 1366×768, 1080p laptops at 125–150 %). Up to the 1920×1080 reference the UI is 1:1, above it grows gently (capped at 1.12). Retina exception (`resolution ≥ 2dppx`, read through a media query because `window.devicePixelRatio` is capped for Mapbox in `runtimeProfile.ts`): below the reference the scale takes half the deficit, floor 0.85 (MacBook Air 13" ≈ 0.87, MBP 14" ≈ 0.89) — 1:1 looked oversized on MacBooks and pushed toolbars onto two rows. The scale is applied with CSS `zoom` (`appScaleStyle`, transform fallback only where `zoom` isn't standard), never `transform: scale()`, which resamples text. The LiDAR viewer applies the same scale to its floating panels (`zoom: var(--app-scale)`). Small windows reflow instead (`pages/Dashboard/lib/layout.ts`): side panels shrink, then alternate (`resolveSidePanels`: the last opened stays) when the center column would drop under 560 px; below 846 px of height (`isShortCanvas`) the map tools become a 2-column grid of 32 px buttons and the center panel gets denser/shorter (240 px min). Below 820×500 a dismissible "window too small" overlay shows (`useIsMobileDevice`). Text floor is 11 px (`xs`); `2xs`/`3xs` are for badge digits and map markers only. Toolbars never wrap: the map search + filter chips (`DashboardPlaceSearch`: search field and chip labels shrink with an ellipsis, then `--tight` chips; labels are only dropped (`--icons`) on an extremely narrow map) and the center analysis toolbar (`useToolbarFitDensity`, 8 measured steps ending in ellipsis on every label, full text in `title`). `npm run bench:screens` (needs `npm run dev`: it uses the dev demo account) drives the real dashboard in headless Edge over 15 screens (half-screen 1080p, laptops at 125–150 %, MacBooks, 1440p, 4K, ultrawide…) plus a 1080p window with an ~800 px left panel, and fails on any text under 11 px (11 × 0.85 on Retina), a `transform` scale, a toolbar on two rows, overlapping/overflowing panels, a menu/context menu/resize not aligned with the pointer, a Mapbox canvas not covering its container, or `styledata` events firing while the map is at rest (style-mutation loop).
- **Mapbox under the canvas zoom**: GL JS measures its container with `getBoundingClientRect()` and only compensates CSS transforms; `map3d/lib/mapContainerZoom.ts` patches `Map#_updateContainerDimensions` to divide by the effective CSS `zoom`, so the transform, canvas, `event.point` and `map.project()` are all in the map container's layout px (without it the 3D map covered appScale² of its area on Retina). Code placing DOM from map px works in layout px (`clientWidth`, `offsetWidth`, `event.point`), never `getBoundingClientRect()` sizes; a rect-measured distance handed to Mapbox (camera padding, `cameraFlight.ts`) is converted with `offsetWidth / rect.width`.
- **Inside the canvas**, viewport media queries and `vw`/`vh` measure the real screen, not the layout: use `@container rv-canvas (…)` and `var(--rv-canvas-width / --rv-canvas-height)`. Overlays portaled to `<body>` must either read the scale from their anchor (`readAppScale`) and position themselves with `appScaledOverlayStyle` (dropdown pattern; pass `inScaledLayer` when portaled into a scaled layer) or use `.rv-app-scaled-layer` (full-screen layers, `src/index.css`). A toolbar that may overflow a narrow column scrolls horizontally with edge fades (`useHorizontalScrollOverflow`) or wraps; it never clips controls.

### Themes (light / dark)
The settings' « Préférence d'affichage » (système / clair / sombre, `displayMode` in the project-browser settings) is resolved by `shared/lib/appTheme.ts` (`initAppTheme()` in `main.tsx` before the first render, `setAppThemePreference` from `SettingsPanel`, follows the OS while on « système ») into `<html data-rv-theme="light|dark">`; the default is « système ». Dark is the original theme and keeps its exact values; tokens live in `shared/styles/theme.css` (glass in `glass.css`, menus in `dropdown.css`). Colour rules in features: text, hairlines and translucent fills are the ink `rgb(var(--rv-ink) / α)` (white in dark, #111114 in light, same α), solid text `var(--rv-text)`; text/icons on the red or another solid colour `var(--rv-on-accent)` (white in both); a value specific to one theme is `light-dark(<light>, <dark>)` (`color-scheme` is set with the theme; `light-dark()` only takes colours, never a length or an alpha). Never write a literal white/black neutral in new UI. Light-theme design: white glass panels (0.9) with a soft `--rv-float-shadow` (never `none`: it composes with other shadows), raised elements white on a light-grey well (`--rvi-tl-card-surface`), status text in the dark tones (#b42318 / #b54708 / #067647), brand red and data colours unchanged. Map content (markers, their badges, route lines, labels) is identical in both themes; popups, menus, legends and cards follow the theme. White monochrome SVG icons must be masks painted with `currentColor`/`--rv-text` (`AssetIcon`, `SvgV2Icon`), not `<img>` (HTML-string popups darken theirs with a light-theme `filter: brightness(0)` rule); the logo goes through `RedViewLogo`. Canvas/WebGL/Stripe colours read `useAppTheme()` (chart slope outline, `stripeAppearance.ts`). The LiDAR viewer stays dark (it imports `theme.css` without initialising the theme).

### Client-side tile pipeline (Service Worker)
`public/sw-dem.js` is a thin entry that `importScripts()` modules under `public/sw-dem/{core,sources,processing,swiss,norway,spain,runtime,workers}`. It builds DEM, ortho, slope and altitude tiles in the browser from public sources (IGN, AWS Terrarium, swissALTI3D, Norway/Spain WCS); it returns 204 on real misses rather than synthesising flat tiles. Contract: the page (`features/map3d/hooks/useMap/serviceWorker.ts`) registers the SW, waits for `controllerchange`, and only then adds `/dem-tiles/` and `/ortho-tiles/` sources. **When you change anything under `public/sw-dem*`, bump the cache stamp in the header comment of `sw-dem.js`** so browsers see a byte diff and purge old caches. Analogous client cache invalidation for the app itself is `shared/lib/appCacheEpoch.ts` (`APP_CACHE_FIX_EPOCH` + build id from `VERCEL_GIT_COMMIT_SHA`/`GITHUB_SHA`).

On the Satellite basemap, `/vhr-tiles` (`sw-dem/sources/vhr-ortho.js`, attached by `useMap/controller/vhrOrtho.ts` right above the `mapbox.satellite` layer, z18–21, always 512 px tiles) overlays the IGN very-high-resolution orthos — `PCRS.LAMB93` 5 cm, then `THR.ORTHOIMAGERY.ORTHOPHOTOS` 5–10 cm — through WMS-R in EPSG:3857, and answers a transparent tile elsewhere so Mapbox shows (Mapbox Satellite in France is the IGN 20 cm ortho up to z19). `transformRequest` (`map3d/lib/satelliteTiles.ts`) also forces the `@2x` Mapbox Satellite tiles (GL JS only asks them at DPR ≥ 2, which the app's DPR cap rarely reaches): the terrain drape textures are 2× the screen, and 256 px tiles upscaled into them lost up to ~20 % sharpness at some zooms. The WMS paints no-data **pure white** (PNG is RGB-only, `TRANSPARENT`/`BGCOLOR` ignored): coverage comes from per-layer 64 px z14 masks, and border-connected white is cleared on the tile itself.

Slope and altitude overlays use `TERRAIN_ALIGNED_RASTER_TILE_SIZE` (`map3d/lib/sources.ts`) so Mapbox requests exactly the tiles of the terrain's DEM pyramid (`floor(zoom − 1)`); the SW then reads the DEM tile the 3D mesh already loaded. The altitude overlay goes further: outside an analysis zone it is a Mapbox custom source (`altitude/lib/altitude-dem-source.ts`) that re-encodes, in memory, the DEM tile the terrain already decoded (`tile.dem`) — no second download (as a raster source on the same URLs it queued behind the terrain and landed 1–2 s later), and it reloads a tile when the terrain replaces its DEM; only the zone-masked path still uses `/altitude-tiles`. A 256/512 px overlay would ask 1–3 zoom levels deeper and force the SW to build its own DEM pyramid (16–64× the IGN traffic). Slope tiles are never answered with a cancellation placeholder: a provisional tile (missing neighbour, stand-in DEM) is rebuilt when the DEM lands (`notifySlopeDemTileReady` → `SLOPE_TILES_STALE` → page reloads the source).

### i18n
UI strings are **the French/English source text itself**: components call `t('Texte français ou anglais')` (`useAppI18n`) or `translateAppText(...)`; translations are `{ fr: '...', en: '...' }` pairs in `src/shared/i18n/config/translations/*.ts`. `AppI18nProvider` additionally translates DOM text nodes and `aria-label`/`placeholder`/`title` attributes through a MutationObserver, so a new user-visible string needs a pair added or it won't translate. The API layer uses `api/_lib/translations-data.ts`, which is **generated** by `scripts/prebuild-api-i18n.mjs` (regex-extracts `{ fr: '…', en: '…' }` literals from every file of `translations/` except `index.ts`) — don't edit it by hand, and keep pairs as single-object literals with quoted strings (no template literals) so the regex still matches. One pair file per area (`global`, `dashboard`, `itinerary`, `lidar`, `map`, `app`, `auth`, `fitPredictor`, …); a new file must also be spread into `translations/index.ts`. On a duplicate key the later pair wins, but the locale's own keys always beat the other language's (a text already in the target language stays itself). The DOM translator only matches whole text nodes: a template literal (`` `${n} fichiers` ``) never translates — use `t('{{count}} fichiers', { count: n })`; canvas/WebGL/Mapbox text-field strings need `translateAppText` explicitly. The LiDAR viewer (`viewer.html`, no React) runs the same DOM observer (`shared/i18n/domTranslation.ts`) from `lidar/viewer/main.ts`. `npm run i18n:audit` (`scripts/i18n-audit.mjs`, `--list` for details) reports coverage, missing strings, untranslatable template literals and conflicting pairs.

## Build/TS conventions
- Path alias `@/*` → `src/*` (tsconfig + Vite).
- `tsconfig.app.json` is strict with `noUnusedLocals`, `noUnusedParameters`, `verbatimModuleSyntax` (use `import type`), and `erasableSyntaxOnly` (no `enum`, namespaces, or constructor parameter properties).
- Env: browser-exposed vars are `VITE_*`; server-only secrets (Stripe, Appwrite API key, upstream URLs) are read from `process.env` in `api/`. `.env` is git-ignored — copy from `.env.example`.
- `.claudeignore` excludes `node_modules`, `dist`, `vendor/redviewalgo/target`, images/wasm and large geodata (`public/france-border.json`, POI icons, etc.).
