# CLAUDE.md

Ce fichier guide Claude Code (claude.ai/code) quand il travaille sur le code de ce dépôt.

## Ce que c'est

RedView est une application 3D de planification et d'analyse d'itinéraires pour l'ultra-cyclisme, le bikepacking et le trail (SPA React 19 + TypeScript + Vite sur Mapbox GL JS v3). Le dépôt est en français : documentation (`docs/` : architecture et plans, audits datés dans `docs/audits/`, index dans `docs/README.md`), commentaires, README et messages de commit ; les identifiants restent en anglais. Les commits suivent les Conventional Commits avec une portée, p. ex. `fix(chart,map): ...`.

**Tests.** Les tests unitaires sont en Vitest (`vitest.config.ts`, autonome : il ne doit jamais importer `vite.config.ts`, dont le plugin de dev charge `.env`, démarre BRouter/POI et ouvre le tunnel SSH). Ils sont à côté du module (`foo.ts` → `foo.test.ts`, `import { describe, it, expect } from 'vitest'` explicite), ceux du serveur dans `server/lib/__tests__/`, `server/multiplayer/` et `api/_lib/__tests__/`, ceux du Service Worker des tuiles dans `test/service-worker/` (`public/` est servi tel quel et ne peut pas les contenir) ; `.dockerignore` les garde hors de l'image. Les tests de composants React passent par `src/shared/test/renderComponent.ts` (et `renderHook.ts` pour les hooks), en `// @vitest-environment happy-dom`. Les écrire d'abord pour la logique métier pure (frontières de sécurité, persistance, calculs de routage, règles d'interface). Les bancs de `script-test-bench/` (lancés avec `tsx`) restent pour les régressions lourdes / de performance / sur données réelles, et `scripts/probes/` contient des sondes ponctuelles contre les services du VPS. Le typage passe par `tsc -b` : l'app (`src`), `vite.config.ts`/`vitest.config.ts`, et `api/` + les tests serveur (`tsconfig.api.json`, `allowJs` pour que les imports de `server/**/*.mjs` soient typés).

**Cliquet ESLint.** Les erreurs ESLint préexistantes sont figées dans `eslint-suppressions.json` (suppressions groupées d'ESLint) : toute nouvelle erreur fait échouer `npm run lint` ; après avoir corrigé une erreur figée, `npm run lint:prune` (le contrôle échoue aussi sur des suppressions périmées). Les noms préfixés par `_` sont volontairement inutilisés (même règle que `noUnusedParameters` de tsc). Ne jamais ajouter de suppression pour faire passer un changement : corriger l'erreur.

`npm run deploy` ne déploie que le travail commité : il s'arrête tout de suite sur un arbre de travail modifié (plusieurs sessions partagent ce dépôt ; l'ancien `git add .` embarquait le travail en cours de tout le monde dans un seul commit non décrit) — commiter d'abord par sujet, ou `npm run deploy -- --commit-all "<type(portée): message>"` pour l'ancien comportement qui commite tout. Il lance ensuite la contrôle qualité (`scripts/quality/check.mjs --full`) sur cet arbre, puis compare le schéma Appwrite de production avec `scripts/appwrite/setup-appwrite-schema.mjs` (`--check`, lecture seule, nécessite `APPWRITE_API_KEY` dans `.env` ; une nouvelle collection / un nouvel attribut / bucket doit être appliqué avec le même script avant de déployer le code qui l'utilise) ; en cas d'échec rien n'est commité ni poussé (`--skip-checks` n'existe que pour les urgences et laisse un trailer `Checks-Skipped: true`). Il pousse ensuite sur `origin/main` et déclenche le déploiement Coolify en SSH sur le VPS de production. Ne jamais le lancer sans demande. `npm run rollback` liste les images que Coolify garde par commit (app et serveur temps réel, celle qui tourne marquée) ; `npm run rollback -- <sha> [--app-only]` relance cette image déjà construite (sans build, les deux services par défaut ; aides Coolify partagées dans `scripts/release/lib/coolify.mjs`) — le code seulement, jamais le schéma ni les données, et `main` contient toujours le mauvais commit : l'annuler (revert) avant le déploiement suivant. Même règle : jamais sans demande. La CI (`.github/workflows/ci.yml`) lance le même `check:full` à chaque push et PR vers `main` (les infos de build de tsc et le cache ESLint — `--cache-strategy content`, un checkout remet les dates à zéro — sont mis en cache après `npm ci`, qui vide `node_modules`), plus le visualiseur LiDAR sous Linux et gitleaks sur tout l'historique.

### Moteur de prédiction Rust / WASM

`vendor/redviewalgo/` est une crate Rust : le moteur vélo v2 de temps en mouvement (`src/cycling/` : physique + comportement simulés sur une grille de ~10 m — politique de puissance selon la pente, vitesse de confort en descente, rayon de virage √(a_lat·R) avec freinage / relance, surface, marche, échauffement / endurance ; préréglages de niveau dans `cycling/presets.rs` ; calibration FIT avec validation croisée intégrée dans `cycling/calibrate/`), le moteur course à pied (`src/running/`, KNN), l'analyse FIT / GPX. Le moteur vélo renvoie **le temps en mouvement seulement et ne prend aucune pause** — les pauses appartiennent à l'horaire de l'app (`pauseAwareSchedule`). Incrémenter ensemble `ENGINE_VERSION` (`cycling/mod.rs`) et `CYCLING_ENGINE_VERSION` (`fitPredictor/engine/version.ts`) quand les résultats changent : les anciennes prédictions vélo persistées sont recalculées.

Recompiler avec `powershell -File vendor/redviewalgo/build.ps1` (sans wasm-pack) : il appelle directement la chaîne rustup, vérifie la version de la CLI wasm-bindgen contre `Cargo.lock`, lance les tests unitaires en wasm32 sous Node (`wasm-bindgen-test-runner` ; dans les modules de test, masquer `#[test]` par `wasm_bindgen_test` sous `cfg(target_arch = "wasm32")`, les tests natifs ne peuvent pas être liés sous windows-gnu), puis écrit la glue JS + le `.wasm` dans `src/features/fitPredictor/engine/pkg/` et copie `redviewalgo_bg.wasm` dans `public/`. `-OutDir <dossier>` compile ailleurs sans toucher à l'app ; `-SkipTests` saute les tests. Les deux sorties sont commitées ; `target/` est ignoré. Le build n'est pas reproductible au bit près d'un dossier à l'autre (section de données) : pour vérifier qu'un changement de commentaires ne change rien, comparer les sections de code. Le frontend ne lui parle que par un Web Worker (`fitPredictor/engine/api.ts` → `worker.ts` ; chemin vélo dans `itineraryPanel/hooks/useItineraryFitRuntime/cycling.ts`).

`vendor/redviewlaz/` est une seconde petite crate Rust (laz-rs) : le décodeur de chunks COPC du visualiseur LiDAR, avec décompression sélective LAZ 1.4 (seulement X/Y/Z, classification, intensité, RVB ; temps GPS, angle de scan, source du point, données utilisateur et drapeaux sautés) — ≈ 2× laz-perf sur les tuiles IGN, sortie identique à l'octet près. `powershell -File vendor/redviewlaz/build.ps1` (même recette de chaîne d'outils et tests wasm32) écrit `src/features/lidar/lib/laz/pkg/` (commité ; Vite émet le `.wasm` comme ressource). Le module est compilé une fois sur le fil principal (`lib/laz/redviewLazModule.ts`, la CSP de Firefox refuse la compilation dans un worker) et confié aux workers de décodage ; laz-perf reste le repli (pas de module, ou erreur de décodage). `lib/laz/redviewLaz.test.ts` compare les deux sur deux vrais chunks IGN.

Banc de justesse : `npm run bench:pace` (`script-test-bench/pace-accuracy/`, vraies sorties FIT Chamonix→Paris + scénarios physiques synthétiques, sortie non nulle sur l'échec d'un critère strict) ; `npm run bench:pace:prep` récupère une fois les tags OSM (proxy BRouter de prod) et le vent historique ERA5 dans un cache ignoré par git (vent tiré d'un conteneur Open-Meteo jetable qui lit les données ouvertes CC BY d'Open-Meteo sur AWS, `PACE_WIND_ARCHIVE` — jamais l'API publique ; commandes dans `lib/wind.ts` ; sans lui R9 est rapporté « non mesuré ») ; `npm run bench:pace:realism` compare des cols célèbres (géométrie BRouter, altitude IGN), les vitesses sur le plat et le GT20 à des références publiques. Les fichiers FIT ne sont pas dans le dépôt (`PACE_FIT_DIR`, ou `REDVIEW_BENCH_DATA`).

Banc de routage : `npm run bench:routing -- --label <nom>` (`script-test-bench/routing-quality/`) passe ~660 scénarios (9 préréglages vélo + variantes + course / trail, 15–1 200 km) par le vrai pipeline client + `api/brouter.ts` contre le BRouter de prod, ce qui nécessite un tunnel SSH (`ssh -i ~/.ssh/oracle_brouter.key -N -L 27777:127.0.0.1:17777 opc@141.145.220.99` ; le `/brouter` de nginx est fermé au public). Il reste séquentiel (`--concurrency` ≤ 2) pour laisser libres les 4 threads BRouter de la prod, et reprend une exécution interrompue. `bench:routing:sweep` calibre le coefficient A*, `bench:routing:compare -- --before a --after b` écrit `reports/routing-quality/ROUTING_QUALITY_REPORT.md` avec des garde-fous (sortie non nulle en cas d'échec), `bench:routing:report` la page HTML. La latence à travers le tunnel dépend de la ligne du client : pour des chiffres fidèles, construire `routing-quality/vps/build-vps.mjs` (bundle en un fichier, Node ≥ 20) et le lancer sur le VPS à côté de BRouter.

## Architecture

### Quatre éléments déployables
1. **SPA frontend** (`src/`) — deux entrées HTML Vite : `index.html` (l'app) et `viewer.html` (servi sur `/viewer`).
2. **API Node « façon serverless » + serveur statique** — `api/*.ts` sont des gestionnaires façon Vercel (`(req, res)` avec `req.query`, `req.body`, `res.status().json()`). Ils sont exécutés par **deux adaptateurs distincts qui doivent rester synchronisés** : le `redviewDevApiPlugin` de `vite.config.ts` (dev, via `ssrLoadModule`) et `server.mjs` (prod, Docker/Coolify, `node:22-alpine`, `Dockerfile`). Dans l'image, `server.mjs` et chaque route sont bundlés par esbuild dans `dist-server/` et lancés par `node` simple, sans tsx (`scripts/build/build-server.mjs` : routes en `dist-server/api/<route>.mjs`, `process.env.REDVIEW_SERVER_BUNDLE` défini au build ; seules les `dependencies` de package.json restent externes et sont installées dans l'image — les paquets réservés au navigateur sont des `devDependencies`, et une devDependency bundlée fait échouer le build). Les fichiers statiques sont précompressés au build (`scripts/build/precompress-dist.mjs`, règle dans `server/lib/static-compression.mjs`) : `server.mjs` sert les variantes `.br`/`.gz` par négociation et ne compresse jamais à l'exécution quand elles existent. Les réponses d'API sont, elles, compressées par `server.mjs` (`server/lib/api-compression.mjs` : JSON / texte ≥ 1 Kio, brotli 4 ou gzip 6, hors de la boucle d'événements au-delà de 64 Kio) sauf si le gestionnaire a déjà posé `Content-Encoding` ; le plugin de dev ne compresse pas. Chaque cache serveur en mémoire est borné en octets avec `server/lib/byte-lru.mjs` (les conteneurs ont des limites de mémoire) — un nouveau cache doit l'utiliser ; une `Map` bornée qui évince par la tête prend la clé dans `server/lib/oldest-key.mjs`, jamais `keys().next()` (V8 rebalaie chaque emplacement supprimé depuis le début de la table : ~10 µs par éviction à 50 000 clés). Les deux associent `/api/<nom>` → `api/<nom>.ts`, ramènent `/api/openmeteo/*` et `/api/weather/*` (server.mjs aussi `/api/brouter/*`) sur un seul fichier, servent tous deux les tuiles de repli que demande une page sans Service Worker (`/radar-tiles`, `/slope-tiles`, `/altitude-tiles` ; `/dem-tiles`, `/vhr-tiles` et les préchargements `?pf=1` répondent 204) via `server/lib/tile-fallbacks.mjs`, et décodent `req.query`/`req.body` via `server/lib/api-request.mjs` (requête à prototype nul). Une nouvelle forme de route d'API demande en général des changements aux deux endroits ; une nouvelle famille de tuiles va dans `tile-fallbacks.mjs`. La normalisation des chemins, la résolution des routes `/api` (pas de `_lib/`, pas de `..` encodé), les limites de taille de corps (`bodyLimitFor`), les clés IP client / limitation de débit, la validation des coordonnées de tuiles, la liste blanche des hôtes radar et celle des amonts de `/api/pointcloud` (sources LiDAR sans CORS : sous-tuiles AHN de GeoTiles, bandes DHMV II d'EODaS OpenLidar — diffusées avec `Range`, jamais mises en tampon) vivent dans le module partagé `server/lib/http-security.mjs`, utilisé par les deux adaptateurs — les changer là, pas dans chaque adaptateur. `server.mjs` possède aussi la limitation de débit en mémoire et les en-têtes de sécurité ; la CSP vit dans `server/lib/csp.mjs` (`buildCspHeader`, posée sur les pages HTML et les scripts de worker ; pas de `'unsafe-eval'` : WebAssembly n'a besoin que de `'wasm-unsafe-eval'` ; les violations sont rapportées au point d'accès sécurité de GlitchTip) — **tout nouvel hôte externe auquel parle le navigateur (serveurs de tuiles, API) doit être ajouté à cette CSP** ; `bench:lidar-engines` sert le visualiseur sous elle dans Chromium et Firefox et échoue sur toute violation.
   **Observabilité** (adaptateur de prod seulement ; le plugin de dev n'en a volontairement pas). Les erreurs partent vers **GlitchTip** auto-hébergé (`errors.redview.tech`, protocole Sentry — pas Sentry). Front : `@sentry/react` dans `src/main.tsx`, release = identifiant de build ; chaque URL de page et de fil d'Ariane est réduite à son chemin avant l'envoi (`shared/lib/errorReportScrub.ts` : les liens de réinitialisation portent `?userId&secret&email`, les requêtes portent des coordonnées). L'identifiant de build a une seule source, `server/lib/build-id.mjs` (define de Vite, étiquette des sourcemaps, release serveur). Les sourcemaps sont construites en `hidden` ; le builder Docker lance `scripts/build/upload-sourcemaps.mjs`, qui utilise `glitchtip-cli` (SHA-256 épinglé ; l'envoi par morceaux de sentry-cli ne fonctionne pas avec GlitchTip) pour injecter les debug IDs dans `dist/assets` seulement (jamais dans les scripts du SW de `public/`), envoyer les maps, puis supprimer chaque `.map`. `server.mjs` répond aussi 404 à tout `.map`. Serveur : `server/lib/observability.mjs` (`@sentry/node`, seulement avec `SENTRY_DSN_SERVER`, erreurs seulement, étiquettes route / id de requête / méthode posées dans un `withScope` local, nettoyé des en-têtes / requête / corps / IP, vidé au SIGTERM) et `server/lib/request-logging.mjs` (pino-http : une ligne JSON par requête sur stdout avec méthode, route **normalisée** (`normalizeRoutePath`, que le serveur pose sur `req.redviewRoute`), statut, durée, `X-Request-ID` (un identifiant entrant sûr est gardé, sinon un UUID ; renvoyé dans la réponse et exposé aux gestionnaires en `req.requestId`) et identifiant de build ; jamais l'URL brute, la requête ni les en-têtes ; un `/health` en 2xx est silencieux, les ressources statiques journalisent en debug, `LOG_LEVEL`). `api/poi.ts` transmet `X-Request-ID` au serveur de POI, dont le journal Fastify écrit des lignes de même forme (`server/poi-server/server.js`).
3. **Serveur de co-édition en temps réel** (`server/multiplayer/`, service Coolify `redview-multiplayer` construit depuis `Dockerfile.multiplayer` — l'image exécute le bundle esbuild `dist-server/multiplayer.mjs`, moteur collab de `src/` compris —, déployé par `npm run deploy` avant l'app) : son port n'est publié que sur `127.0.0.1:17790`, et le **nginx de l'hôte** (`/etc/nginx/conf.d/app.conf`, qui relaie aussi l'app vers `127.0.0.1:3000`) lui envoie `/multiplayer` avec les en-têtes WebSocket — le trafic public ne passe jamais par les labels Traefik de Coolify. L'app n'affiche « Partager » que si `/multiplayer/health` répond `{"ok":true}` (c'est tout ce qu'il répond ; un chemin inconnu renvoie l'`index.html` de la SPA avec 200). Les mesures (salles, clients, latence du journal / des points de reprise, erreurs, validation fantôme, retard de la boucle d'événements, tas) sont servies sur le port interne 17791 du conteneur seulement, jamais relayé : `sudo docker exec $(sudo docker ps -q -f name=krejrvgvs2w5kmfo27rutffz) wget -qO- http://127.0.0.1:17791/metrics.json` (`/metrics` = texte Prometheus). Les erreurs partent vers GlitchTip quand `SENTRY_DSN_SERVER` est défini sur ce service (même `server/lib/observability.mjs`). Voir `features/collab` plus bas.
4. **Microservices du VPS** (VPS Oracle derrière nginx, joignables via les proxys de `api/` par `BROUTER_UPSTREAM`, `POI_UPSTREAM`, `WEATHER_UPSTREAM` — voir `.env.example`) :
   - BRouter autonome (port 17777) — moteur de routage ; `api/brouter.ts` met les paramètres de requête en liste blanche et envoie les profils BRF dynamiques. En dev, `scripts/dev/start-dev-services.mjs` en démarre un local si un dépôt voisin `../redview-brouter` existe. Le frontend produit à chaque changement un profil BRF neuf d'environ 500 lignes à partir des curseurs de l'interface (`brf-template.ts`) ; voir `docs/architecture/routing.md`. La recherche est toujours en une passe (`pass2coefficient=-1`) ; le `pass1coefficient` d'A* est fixé par requête à partir du coût par mètre du profil (estimé dans `brf-template/values.ts`, puis appris des réponses) et de la distance (`lib/brouter/api/searchCoefficient.ts`, borné côté serveur par `api/_lib/brouter-search.ts` — mêmes paliers de distance des deux côtés, garantis par `searchCoefficient.test.ts`). Chaque itinéraire est routé avec son profil produit, même avec des curseurs neutres — jamais un profil BRouter standard (`routing-resolver.ts` ; un échec d'envoi est réessayé une fois, puis signalé). Les tronçons de plus de ~180 km sont d'abord routés grossièrement, puis affinés entre des ancres posées sur le tracé grossier (`routing/long-distance-anchors.ts`, orchestré dans `useItineraryBrouterRouting/resolveRouteRequest.ts`) ; une recherche fine lente est doublée par une plus gourmande après un délai fonction de la distance (`customProfileFetch.ts`), et si elle dépasse encore son délai, la même méthode d'ancres repart avec des ancres plus serrées (puis une recherche grossière plus gourmande) au lieu de tout profil de repli. Les délais s'arrêtent aux en-têtes de réponse, pas au téléchargement. Les modifications locales (déplacer / insérer / retirer un point, zone interdite, sur des routes BRouter comme sur des GPX importés) ne reroutent qu'une fenêtre du tracé enregistré autour de la modification, ±12 km d'abord, élargie à ±80 puis ±200 km et aux vraies bornes seulement quand le nouveau tracé ne rejoint pas l'ancien (`narrowRoutePatchToEdit`, `WINDOW_STEPS_M` dans `useItineraryBrouterRoutingShared/routePatchWindow.ts` : le temps de recherche croît bien plus vite que la longueur, une première fenêtre de ±80 km coûtait des secondes par glisser) ; un correctif en attente est routé par une tâche par itinéraire (`ensurePatchJob` dans `useItineraryBrouterRouting`), pour l'itinéraire sélectionné comme pour les autres, si bien qu'une modification sur un itinéraire non sélectionné, ou un changement de sélection en plein reroutage, n'est jamais laissé non routé (l'ajout en fin de tracé et le recalcul complet restent sur l'itinéraire sélectionné) ; les bornes de correctif prises sur le tracé portent leur `distanceM`. **Un tracé enregistré ne contient jamais de ligne droite** (elles finissent dans l'export GPX) : chaque jonction de morceaux de tracé (correctif, prolongement, tronçons de requête, recalcul, fusion) doit se rejoindre à moins de `ROUTE_SEAM_TOLERANCE_M` (`lib/routes/route-continuity.ts`) ; les bornes intermédiaires d'un correctif sont demandées sur le tracé enregistré (`anchorRoutePatchBound`) et raccordées là où le morceau routé le rejoint vraiment (`planRouteSplice`, dans `useItineraryBrouterRoutingShared/routeSplice.ts`), une borne `start`/`end` remplace tout ce qui est avant / après elle, et une jonction qui échoue élargit la fenêtre puis se replie sur un recalcul complet (`RouteSeamError`), jamais une ligne. Un départ / une arrivée posés sur le tracé le rognent sans routage (`cropRoutePoints`, `placeRouteEndpoint` dans `ItineraryPanelContainer/routeEndpointPlacement.ts`) ; les gestes à main levée du visualiseur LiDAR sur un itinéraire routé sont traduits en ces mêmes modifications de l'app (`lidarViewerRouteEdit.ts`) ; les sauts entre segments GPX et les fichiers `<rte>` clairsemés sont routés à l'import (`importedGpxGaps.ts`) ; les anciens artefacts de départ / arrivée sont retirés à la normalisation (`repair-route-endpoints.ts`). Contrôles : `npx tsx script-test-bench/route-continuity/run.ts` (BRouter de prod via un tunnel) et `node script-test-bench/route-continuity/e2e.mjs` (nécessite `npm run dev`). `api/brouter.ts` compresse lui-même le GeoJSON des routes (brotli / gzip, gardé compressé dans son cache), donc `server.mjs` laisse ces corps tranquilles.
   - `server/poi-server/` — serveur de POI Fastify + SQLite/R*Tree (port 17778), construit par `server/poi-ingest/`.
   - `server/weather-daemon/` — ingestion GRIB en Python + serveur de tuiles (unités systemd, configuration nginx).
   - Open-Meteo auto-hébergé (`server/vps/open-meteo/docker-compose.yml`, 127.0.0.1:8080, nginx `/openmeteo/`, `OPENMETEO_UPSTREAM`) : la seule source des prévisions ponctuelles (`/api/openmeteo`, météo de route, vent, menu contextuel de la carte) et de l'historique météo du modèle neige — **jamais l'API publique api.open-meteo.com** (licence non commerciale ; le navigateur ne peut pas la joindre, CSP). Périmètre décidé avec l'utilisateur : France et pays voisins, J+4, ≤ 5 Go — AROME France 0,025° (51 h) + ARPEGE Europe 0,1° (4 jours) de Météo-France synchronisés en local (`sync … --execute` purge les anciens fichiers ; 62 jours des 5 variables ARPEGE du modèle neige), ~1,9 Go, aucune lecture S3 à la demande (≥ 60 s pour une requête de 200 points). Les clients demandent `models=meteofrance_seamless` (`OPENMETEO_MODEL`), horizon `OPENMETEO_FORECAST_DAYS` = 4 ; `api/_lib/openMeteo.ts` valide le modèle (anciens `best_match`/AROME HD convertis), borne les jours et plafonne à 200 lieux. Pas de climat (CMIP6) ni d'API d'altitude : l'altitude des routes hors de France vient des tuiles Terrarium (`shared/lib/terrarium.ts`). Une nouvelle variable ou un nouveau modèle doit être ajouté à la synchronisation et tenir dans le budget.
   - La configuration de l'hôte (unité BRouter et son tas de 3 Go, compléments systemd de ressources, sysctl, journald, `daemon.json` de Docker, surcharge compose d'Appwrite) est versionnée dans `server/vps/` — son README dit où va chaque fichier, comment appliquer / revenir en arrière, et le **plancher mémoire Always Free** (Oracle récupère une instance A1 inactive quand processeur, réseau *et* mémoire restent sous 20 % pendant 7 jours ; la mémoire est la seule au-dessus : garder la RAM utilisée ≥ 25 %). `bash scripts/vps/perf-snapshot.sh <libellé>` prend un instantané avant / après en lecture seule.

Un nouveau service public ou une nouvelle dépendance du VPS y reçoit un contrôle ; `sudo /usr/local/sbin/redview-watch check` les montre tous.
   - **Sauvegardes** (`server/vps/backup/`, README = procédure de reprise après sinistre) : `redview-backup.timer` lance `/usr/local/sbin/redview-backup run` chaque nuit à 02:30 UTC — dumps logiques faits dans chaque conteneur de base (MariaDB d'Appwrite sans les données `_1_audit`, PostgreSQL de Coolify / GlitchTip / Umami), volumes Appwrite, `/opt/appwrite/.env` (son `_APP_OPENSSL_KEY_V1` déchiffre les fichiers stockés), `/data/coolify/source/.env` (APP_KEY), `/etc`, services et un manifeste système → restic (chiffré, dédupliqué) → Google Drive `RedView-Restic` via rclone (client OAuth propre, portée `drive.file` : le jeton du VPS ne voit que ce que rclone a créé) ; rétention 7 quotidiennes / 5 hebdomadaires / 12 mensuelles. `redview-backup-verify.timer` (dimanche 04:30 UTC) : purge, `check --read-data-subset n/12`, un vrai exercice de restauration (dumps rechargés dans des conteneurs tmpfs jetables, nombres de lignes comparés ; 40 fichiers Appwrite comparés octet par octet ; fichiers critiques présents) et un e-mail de rapport hebdomadaire ; tout échec ou une baisse de plus de 30 % envoie un e-mail via Resend (`OnFailure=redview-backup-alert@`). Le mot de passe restic doit aussi exister hors du VPS (PC de dev `~/.redview/backup/`, gestionnaire de mots de passe). Les fichiers installés sur l'hôte gardent leur contexte SELinux — toujours `install` + `restorecon` (`install.sh`) : un `cp`/`mv` depuis `/tmp` (`user_tmp_t`) a laissé l'ancien cron mort sans bruit pendant 16 jours. `sudo` n'a pas `/usr/local/sbin` dans son PATH sous Oracle Linux : appeler le chemin complet.

### Structure du frontend (`src/`)
- `App.tsx` gère l'amorçage : session Appwrite, accès selon l'abonnement (pendant la bêta ouverte, tous les inscrits ont accès ; les non-abonnés sont étiquetés `demo`), blocage mobile, puis charge à la demande `pages/Dashboard`. **Chargement initial :** `index.html` peint un écran de démarrage statique (`.rv-boot`, styles en ligne, thème de l'OS tant que `data-rv-theme` n'est pas posé) que `BootstrapScreen` redessine à l'identique : pas de page blanche. La coque du Dashboard (gestionnaire de projets) se charge sans l'éditeur 3D : `DashboardEditor` est `lazy()` (`pages/Dashboard/editorLoader.ts`), préchargé quand le navigateur est inactif, au survol d'une carte de projet (`data-rv-project-card`) et dès qu'un projet commence à s'ouvrir. La coque doit importer des modules concrets, jamais les barrels `map3d`/`controlPanel`, et le provider LiDAR ne tient qu'un emplacement (`lidarManagerSlot.ts` : le `LidarManager` est créé par `useLidarManager()` dans l'éditeur et détruit avec le Dashboard). `npm run bundle:check` (dans `check:full`) échoue si mapbox-gl, mapbox-gl-draw, copc, proj4 ou l'éditeur arrivent sur ce chemin critique, ou s'il dépasse 300 Kio en brotli (271 Kio mesurés, 1 075 Kio avant le découpage).
- `pages/Dashboard` est la racine de composition : il possède l'instance Mapbox et l'état du projet actif, et relie les panneaux des features. La persistance des projets passe par `shared/services/projects/*` (lignes Appwrite + compression + cache IndexedDB dans `shared/services/storage`). La copie IndexedDB (`idbProjectStore.ts`, v3) garde les métadonnées de chaque projet (`projects`) à part de son contenu (`project_data` : JSON du document + travail local) : les lectures / écritures de métadonnées (`dirty`, version cloud, nom, `markLocalSynced`) et la liste des projets ne clonent jamais le document — un projet de 61 M caractères était lu et écrit deux fois par sauvegarde automatique. Une charge gzip de plus de ~12 M caractères (limite du nginx devant Appwrite) part plutôt dans le bucket `project-payloads` (`payloadFiles.ts`, envoi par morceaux, ≤ 30 Mo ≈ 100 Mo de projet) et le `data` de la ligne contient `file:<fileId>` ; tout code qui lit `projects.data` doit gérer ce pointeur. Le gzip + base64 de la charge cloud tourne dans un worker partagé (`payloadEncodingClient.ts` → `payloadWorker.ts`, même résultat dans la page en repli) : sur un projet de 16 M caractères, il bloquait la page 0,85 à 1,3 s par sauvegarde automatique (toutes les 4 s pendant l'édition). Note : d'anciens documents mentionnent Supabase ; le backend réel est **Appwrite** (`shared/services/appwrite.ts`, `node-appwrite` côté serveur dans `api/_lib`).
- **État serveur et toasts.** L'état serveur (listes Appwrite, compte, facturation, API) passe par TanStack Query (`shared/services/queryClient.ts` : périmé après 30 s, pas de nouvel essai sur un 4xx, les mutations en échec affichent un toast sauf `meta.silentError` ; cache vidé à chaque changement de session dans `App.tsx`), un dossier `queries/` par feature (premier : `projectBrowser/queries/projectLibrary.ts`, mises à jour du cache en fonctions pures). Jamais pour le document de l'éditeur (ProjectStore / sauvegarde automatique) ni pour la carte. Les toasts de retour à l'utilisateur passent uniquement par `notify` (`shared/lib/notify.ts`, sonner rendu sans style par `AppToaster`).
- **Données du compte (RGPD).** « Compte → Vos données » (`projectBrowser/account/components/AccountDataForm.tsx`) : export de tout ce que possède le compte (`lib/accountData.ts` : ZIP avec `compte.json` + un `.redview` par projet possédé, construit entrée par entrée avec `StoredZipBuilder`, un seul projet en mémoire à la fois) et suppression du compte confirmée par un code envoyé par e-mail (`DeleteAccountDialog`, `api/auth/delete-account.ts` — sous `auth/` pour la limitation de débit stricte ; codes de `verificationStore` sous `accountDeletionCodeKey`). La purge est `api/_lib/accountDeletion.ts` (idempotente, reprenable : blocage + étiquette `deletionpending`, client Stripe supprimé d'abord, projets possédés via `deleteSharedProject`, départ des autres équipes, fichiers possédés des trois buckets orphelins compris, lignes de vues / dossiers / facturation, puis l'utilisateur Appwrite ; registre `account_deletions` avec identifiants et dates seulement). **Un nouveau type de donnée possédée par l'utilisateur doit être ajouté à cette purge et à l'export.** Les fichiers FIT (traces GPS, fréquence cardiaque : données potentiellement de santé) partent aussi avec leur projet (`deleteProject` efface ceux que le document référence) et avec leur itinéraire (mis en attente tant que la suppression peut s'annuler, effacés à la fermeture du projet s'ils ne sont plus référencés : `usePendingFitDeletions`, `shared/services/projects/fitFiles.ts`) ; un fichier n'est jamais partagé entre deux projets (la duplication crée la copie sans eux, puis lui donne les siens). `npx tsx --env-file=.env scripts/appwrite/fit-orphans.ts` compte les orphelins (lecture seule, `--apply` les efface). Constats et écarts de conformité France / UE : `docs/audits/2026-10-08-conformite-fr-ue.md`. `scripts/appwrite/account-deletions.ts` liste / reprend (`--resume`) les suppressions interrompues et les réapplique (`--reapply`) après une restauration de sauvegarde. La propriété s'établit toujours par les `$permissions` (`corroboratedOwnerId`), jamais par `user_id` seul. **Statistiques** (`docs/analytics/measurement.md`) : uniquement des événements Umami anonymes (`shared/lib/analytics/` : pas d'`identify`, pas de rejeu de session — retiré le 2026-10-07, non exempté de consentement ; catégories, tranches et valeurs arrondies ; chaque charge — Web Vitals du traceur et clics `data-umami-event` compris — passe par `beforeSend.ts` : URL = écran virtuel (`screens.ts`, jamais le vrai chemin `/project/<nom>--<id>` ni le titre), seuls `utm_*`/`ref` gardés, referrer réduit à son origine, garde de confidentialité sur les valeurs, super-propriétés `surface`/`plan`/`account_age`/`lang`/`theme`, rien pour les comptes étiquetés `internal` ; noms, clés de propriété et valeurs partent en français courant via `labels.ts` — ce que lisent dans Umami les lecteurs non techniques ; renommer un libellé y démarre un nouvel événement). Les tableaux de l'équipe sont aussi du code (`scripts/analytics/umami/boards.ts`, guide en langage simple `docs/analytics/stats-guide.md`). Le traceur est servi depuis notre propre domaine (`/s/x.js`, `/s/api/send` relayés par le nginx de l'hôte, `server/vps/nginx-stats.conf`), jamais chargé en dev ni hors de l'hôte de prod (`localStorage['rv:analytics-test']` pour les bancs) ; étiquette Umami = release. Un nouvel événement : son type dans `events.ts`, l'appel au point de passage le plus central, `scripts/analytics/umami/spec.ts` si c'est une étape d'entonnoir (`npm run analytics:sync`) ; `e2e:journey` vérifie les écrans / événements du parcours et qu'aucune charge ne porte d'e-mail, de nom, d'identifiant ni de chemin de projet. L'activation par cohorte d'inscription et l'usage viennent de la base : `npm run analytics:report` (`api/_lib/activationReport.ts`, comptes `internal` exclus, `scripts/analytics/internal-accounts.ts`). Instance : `server/vps/umami/` (3.4 épinglée, MCP, minuteur de rétention de 25 mois).
- `features/*` sont des domaines découpés par feature (`altitude`, `slope`, `snow`, `weather`, `sunlight`, `lidar`, `poi`, `fitPredictor`, `map3d`, `centerPanel`, `controlPanel`, `itineraryPanel`, `projectBrowser`, …). Convention (voir `docs/architecture/structure.md`) : `index.ts` est l'API publique, plus `components/ hooks/ lib/ types.ts` ; importer une feature par son `index.ts` quand il existe — sauf depuis un module que ce barrel réexporte, directement ou transitivement (contextes bas niveau, marqueurs, aides de carte) : y importer le module concret, sinon le barrel ferme un cycle d'import (`npm run cycles` échoue). Chaque feature suit cette coque (`index.ts` seulement quand quelque chose d'extérieur importe la feature ; sous-domaines nommés comme `centerPanel/tools/<outil>/` ou `centerPanel/flyover/` ; `collab/` garde son contrat d'échange — `protocol.ts`, `wire.ts`, `schema.ts`, `realtime.ts`, `routeChunks.ts` — à sa racine pour `server/multiplayer`). `shared/` a sept rôles : `components/`, `hooks/`, `lib/` (fonctions pures et aides du navigateur), `services/` (Appwrite, persistance des projets, client de requêtes), `styles/`, `i18n/`, `test/`. `features/freeCam` est la caméra libre façon jeu vidéo sur la carte 3D (F, ZQSD/WASD, Espace ou Maj = monter, Cmd (Mac) ou Ctrl = descendre — Cmd+W/Q ne peut pas être annulé par la page, donc une confirmation de sortie de page est armée tant que Cmd est enfoncé, et macOS perd les keyup sous Cmd, donc les touches de déplacement sont relâchées avec lui —, regard à la souris sous verrouillage du pointeur, molette = multiplicateur de vitesse ×0,25–16) : la vitesse suit la hauteur au-dessus du sol, et une vélocité (`lib/velocity.ts`, réponse exponentielle indépendante de la fréquence d'images : ~0,4 s jusqu'à pleine vitesse, ~1 s de glisse au relâchement, arrêt net sous 1 % de la vitesse) pilote la pose ; au repos la carte n'est jamais touchée.
- L'objet métier central est `ItineraryProject` (1..N variantes d'itinéraire plus la configuration du cycliste, la vue de la carte et les réglages par panneau). C'est la forme *composée* sur laquelle travaille l'interface ; elle se découpe en trois couches (`itineraryPanel/lib/project/layers.ts`, la source unique, base de la co-édition en temps réel) : le **document** partagé par tous les éditeurs (nom, itinéraires, copies des profils de routage personnalisés qu'ils référencent — `toProjectDocument`, stocké dans `projects.data` sous la forme `{ schema: 2, … }`), la **vue** par utilisateur (`PROJECT_VIEW_KEYS` + `ITINERARY_VIEW_KEYS` : itinéraire / mode actifs, vue de la frise, `controlPanel`, `analysis`, `dashboard`, œil / mode de rendu / opacité de chaque itinéraire — stockée à part dans `views` d'IndexedDB + la collection Appwrite `project_views`, un document par (projet, utilisateur), la dernière écriture gagne, `projectViews.ts`) et le **travail local** par appareil (`ITINERARY_LOCAL_WORK_KEYS` : `pendingRoutePatch`, `pendingTraceExtension`, `pendingFitRecompute` — seulement dans le `work_json` de la copie IndexedDB, jamais dans le cloud : l'appareil qui a fait une modification en calcule le résultat). Un nouveau champ appartient au document par défaut ; un état d'affichage doit être ajouté aux clés de vue. Le Dashboard trie chaque changement avec `classifyProjectChange` : un changement de vue seule ne sérialise ni ne réécrit jamais le projet (pas de version, pas de conflit entre appareils) ; `saveProject` saute un document que le cloud a déjà confirmé. Annuler / rétablir ne touche jamais la vue. Les anciens projets stockés (forme composée, vue et travail à l'intérieur) restent lisibles partout (`readStoredProject`/`storedProject.ts`) ; à la première ouverture, leur vue amorce la vue stockée de l'utilisateur (création seulement, horodatée à la dernière sauvegarde du projet). Les identifiants des éléments du document viennent de `createDocumentId(prefix)` (temps + aléatoire : uniques entre éditeurs). Les profils de routage personnalisés sont la bibliothèque du compte (`prefs.routingProfiles`, miroir local `redview:routing-profiles:v2` avec ajouts / suppressions en attente rejoués sur la copie du compte ; l'ancien `redview_custom_routing_profiles` adopté une fois) ; le sélecteur liste aussi les copies intégrées au projet. `npm run bench:project-layers` vérifie les couches ; `script-test-bench/audit/a-persistence-sim.ts` exécute le vrai code de persistance sur un Appwrite / IndexedDB simulé (scénarios V1–V6, PR1 sur les vues, la migration, le travail local, la collection absente, les profils ; C1e le chemin du bucket `project-payloads` d'un projet de plus de 12 M caractères — le SDK simulé a un Storage en mémoire : envoi, pointeur `file:`, un seul fichier restant après deux sauvegardes, relu en entier sur un autre appareil). `scripts/appwrite/setup-appwrite-schema.mjs --only=project_views` crée la collection (sans elle, les vues restent locales, journalisé une fois).
- `features/collab` est la co-édition en temps réel de la couche document, sur le modèle de Figma : le serveur fait autorité (vue d'ensemble en langage simple, règles de modification, tests : `docs/architecture/collab-realtime.txt`). Le document est aplati en objets à propriétés (`collab/model/` : identifiants dérivés du document — racine `p`, itinéraires `p/itineraries:<id>`, éléments de liste `<parent>/<champ>:<clé>` ; réglages à une propriété par clé, listes à un objet par élément sur un indice fractionnaire (`fractional-indexing`, égalités repositionnées par le serveur), routes en une propriété d'en-tête + des morceaux adressés par contenu, `routeChunks.ts` ; règles de fusion dans `collab/schema.ts`). Les opérations sont `c`/`d`/`s`/`m` (création, suppression avec descendants, affectation = le dernier écrivain gagne par propriété, déplacement) ; `diffDocument` compare par référence (`toItineraryDocument` est mémoïsé par itinéraire, donc les itinéraires inchangés sont sautés), `invertOps`/`applyOpsWithInverse` donnent des inverses exacts, `Materializer` ne reconstruit que les objets remplacés et `adopt()` rend à l'app ses propres objets. Le ProjectStore ne connaît que le contrat `ProjectCollabLink` (`ProjectStore/collab.ts`) : avec un lien, chaque document validé est envoyé (`user`/`step` = actions de l'utilisateur, `background` = résultats asynchrones, `comment` = commentaires : jamais un pas d'annulation, envoyés même avant `welcome`), les documents des autres éditeurs sont recomposés avec la vue et le travail local de cet appareil (`externalRevision` s'incrémente). **Rien de ce qui est saisi pendant la connexion n'est perdu** : `useCollabSession` transmet le lien dès que la session existe (`pending` pendant le chargement de son module : le store enregistre ses écritures et utilise `SESSION_PENDING_COMPUTE_GATE`, aucun calcul périmé), le store appelle `bind(base, changes)` — le document qu'il affichait (point de reprise cloud, ou la copie locale plus fraîche : `getProject` la choisit pour les projets partagés) devient l'état confirmé *provisoire* du client, ses écritures depuis sont rejouées exactement — et seulement ensuite la WebSocket s'ouvre ; jusqu'au premier `welcome`, les modifications de l'utilisateur sont des lots en attente ordinaires, rejoués sur l'instantané du serveur puis envoyés, tandis que les résultats `background` calculés sur la base provisoire restent locaux (`localOnly`, abandonnés au `welcome` : ils écraseraient ceux de la session). Les lots non synchronisés (en attente + acquittés non durables) sont aussi gardés sur l'appareil (`client/unsyncedStore.ts`, IndexedDB `redview-collab`, écrits au plus 250 ms après un changement et au `pagehide`) avec leur `clientId` ; la session suivante du même utilisateur sur ce projet les adopte sous un Web Lock (un seul onglet ; sans Web Locks → rien n'est gardé) et les renvoie, `welcome.clientSeq` dédoublonnant (`client/session.ts`). En-tête : `data-rv-collab-status` (`connecting`/`online`/`offline`) sur `.rvi-header`, une ligne d'état seulement si cela dure (> 1,2 s / 2 s) ; un refus (4404 projet supprimé, 4403 accès retiré) affiche un toast, revient au gestionnaire de projets et supprime la copie de l'appareil. Client (`collab/client/`) : `SyncEngine` (état confirmé au seq N + lots en attente ; visible = confirmé + en attente rejoués, donc une valeur distante sur une propriété que l'on vient de changer est masquée jusqu'à son propre acquittement ; ses propres lots gardés jusqu'à `durable` et renvoyés après un plantage du serveur, `welcome.clientSeq` dit lesquels le serveur a ; hors ligne, les opérations s'ajoutent au dernier lot jamais envoyé (≤ 2 000 opérations, pas de morceaux de route) au lieu d'un lot par vidage, un lot une fois envoyé n'est jamais modifié, et un arriéré part au plus par 4 lots par vidage ≈ 120/s — une longue édition hors ligne renvoyait des milliers de lots d'un coup, touchait la limite de débit du serveur (4429) et bouclait), `UndoHistory` (par utilisateur, inverses côté client, compactés en une écriture par propriété au sein d'une série d'affectations — annuler un glisser continu envoie une opération par propriété, pas une par événement ; ne restaure jamais une propriété que quelqu'un d'autre a changée depuis ; suppressions recréées avec toutes leurs propriétés ; un résultat de fond rejoint le pas de l'action qui l'a causé, donc annuler le déplacement d'un point de passage restaure l'ancien tracé sans routage), `LeaseGate` (`DerivedComputeGate` par baux du serveur : l'auteur du dernier changement des entrées (`DERIVED_INPUTS`) a la priorité pendant 5 s, puis le premier demandeur ; - Rendu LiDAR (`lidar/viewer`) : les tuiles sont diffusées en octrees additifs depuis le cache LOD d'OPFS (`lib/lodCache.ts` v2, 16 o/point : position, classe, intensité, RVB et le RVB / l'intensité filtrés par cellule qu'un nœud affiche là où aucun de ses enfants n'est dessiné, pour que les niveaux grossiers ressemblent à un niveau de mip plutôt qu'à des échantillons poivre et sel ; un cache v1 est mis à niveau à l'ouverture, sans décodage). `SceneLod` choisit les nœuds selon l'espacement projeté sous le budget adaptatif en mouvement (`lodBudget.ts`) ; une fois la caméra arrêtée, `lod/restRefinement.ts` augmente le budget vers ~50 ms de GPU par image fixe (`restMaxBudget` de la plateforme), puis accumule 16 images décalées au sous-pixel en lumière linéaire (`renderScene({ accumulate })`) et se met au repos. Le maillage du MNT est dessiné par chunk de 128 quads au niveau dont la vue a besoin (`renderer/terrainLodCore.ts`, partagé par les deux moteurs : bords recousus, chunks grossiers repoussés le long du rayon de vue de leur erreur de hauteur pour ne jamais masquer un point ; éclairé avec le `shadeSurface` des points) : dessiné en entier (19 M triangles pour 9 tuiles), il bloquait à 1,5 M le budget de points d'un GPU intégré. `npm run bench:lidar-shots` capture des vues fixes d'une vraie scène multituile (avant / après un changement de rendu, `--dist` pour un build conservé) et `bench:lidar-fps` prend `LIDAR_TILES_DIR` pour une scène de 9 tuiles (`--cold` jette d'abord les caches dérivés et affiche la chronologie des étapes de chargement d'une première ouverture : décodage, colorisation par ortho, construction du LOD + écriture OPFS, écrite par une poignée d'accès synchrone dans le worker). Un premier chargement passe par un pipeline à deux étages (`session/sceneMemoryBudget.ts` `TileLoadPipeline`) : décodage (tous les workers de décodage ; ils envoient leurs points par lots d'1 M points copiés directement dans les tableaux de la tuile et s'arrêtent une fois finis, le fichier compressé est jeté une fois découpé — `workers/copcDecodeWorker.ts`) + colorisation + copie du sol, puis construction du LOD + écriture OPFS (un worker) ; la tuile suivante se décode pendant que la précédente se construit, une tuile par étage, quand les deux étages tiennent dans 40 % de `deviceMemory` (38 o/point chacun, nombres lus dans les en-têtes LAS ; une tuile seule passe toujours). La scène de 9 tuiles : 7,65 Go avec trois tuiles à la fois, puis 4,68 Go et 133–171 s une tuile à la fois (morceaux, tableaux assemblés et huit tas WASM qui ne rétrécissent jamais en même temps), maintenant 3,8 Go et 100–109 s sur batterie contre 140–172 s pour le chargement séquentiel (A/B entrelacé, 2026-10-07), caches identiques à l'octet près ; un coût unique, réouverture en cache en 2,1 s. - **Deux moteurs de rendu, un seul visualiseur** (compatibilité Linux). Le visualiseur ne parle qu'à l'interface `LidarRenderer` (`viewer/renderer/sceneRenderer.ts`), implémentée par `WebGpuLidarRenderer` (`viewer/renderer.ts`) et `WebGlLidarRenderer` (`viewer/renderer/webgl/`), chacun un chunk chargé à la demande seulement quand il est choisi. **Ne jamais lire une globale WebGPU (`GPUShaderStage`, `GPUBufferUsage`…) au niveau d'un module** : Firefox sous Linux n'en a aucune, et une seule de ces constantes faisait planter tout le visualiseur à l'import (`noWebGpuApi.test.ts` importe chaque module de rendu sans elles). Les deux dessinent la même image : ombrage paresseux par nœud (WebGL 2 : la passe de calcul WGSL en vertex shader capturé par transform feedback), sprites instanciés à taille adaptative, LOD du terrain par chunks, surcouches, maillages de tracé / d'analyse, trajectoire du soleil, EDL, résolution réduite en mouvement, MSAA sur les GPU dédiés, accumulation rgba16f (nécessite `EXT_color_buffer_float`, sinon les images fixes ne sont pas moyennées) — donc outils, commentaires, édition de tracé, vue à 360° et neige fonctionnent sur les deux. `createLidarRenderer` (`renderer/createRenderer.ts`) prend WebGPU quand la vérification préalable (`renderer/device.ts` : délais de 8 s pour l'adaptateur / 10 s pour le device — certaines piles Vulkan Linux ne répondent jamais ; adaptateurs de repli et logiciels refusés) trouve un adaptateur matériel, sinon WebGL 2 sur un canvas neuf (`renderer/canvas.ts` `claimViewerCanvas` : un canvas garde son premier type de contexte). C'est le chemin habituel sous Linux en 2026 : Firefox ne livre WebGPU que sous Windows / macOS, Chrome ne l'active sous Linux que pour Intel Gen12+ et NVIDIA sous Wayland. Le GLSL de `webgl/glShaders.ts` est un portage ligne à ligne du WGSL qui partage le bloc std140 `Scene` (`packSceneUniforms` remplit les deux) : **un changement d'ombrage / de surcouche va dans les deux**. WebGL n'a pas de contrôle du clipping dans Firefox, donc sa profondeur est conventionnelle avec le near / far de la caméra (`camera.getDepthRange()` → `setDepthRange`, linéarisée par sa passe EDL). `?engine=` : absent = auto, `webgl` = WebGL 2, `terrain` = l'ancien MNT texturé sans points (`viewer-webgl/`), aussi dernier recours quand aucun moteur ne démarre ; deux pertes de contexte GPU en 2 min font passer WebGPU → WebGL 2 → terrain. Le « Moteur » du panneau liste les trois (WebGPU grisé avec la raison quand il est indisponible). Les chaînes de rendu WebGL (ANGLE, Mesa, noms assainis de Firefox) correspondent aux mêmes niveaux de GPU (`resolveWebglPlatformInfo`) ; les rastériseurs CPU (llvmpipe, SwiftShader, WARP) reçoivent le profil `software`. Sans minuteurs GPU (Firefox ne les expose jamais), les images fixes sont jugées sur l'intervalle réel (`FrameClock.lastIntervalMs`, images longues comprises) et une image fixe complète de plus de 200 ms termine l'affinage (`restRefinement.ts`). Les entrées sont indépendantes de la plateforme : le menu des outils s'ouvre au relâchement du bouton droit et `contextmenu` est toujours annulé (Linux l'envoie à l'appui), les deltas de molette sont normalisés (`wheelDeltaPixels` : Firefox rapporte des lignes). `npm run bench:lidar-engines` (Playwright Chromium + Firefox, `--browsers webkit` pour le moteur de Safari — sa version Windows laisse vides les écritures OPFS, donc les tuiles vont dans CacheStorage comme le fait `saveTile` après vérification de la taille écrite ; tuile LAS synthétique, réseau externe coupé ; job CI `viewer-linux` sous Ubuntu avec `--expect-auto webgl` ; un navigateur dont le moteur auto est déjà WebGL 2 saute le cas WebGL forcé, même chemin) vérifie rendu, EDL, modes de couleur, terrain, pentes, ensoleillement, clic droit dans l'ordre Linux, glisser-déplacer, molette en mode lignes et `gl.getError()` ; `bench:lidar-shots -- --params engine=webgl` compare les deux moteurs sur une vraie tuile (2026-10-06, tuile 0965_6500 : différence moyenne ≤ 0,21/255, même sélection LOD).

- `centerPanel/flyover` est la lecture 3D de la route (Lecture dans la barre d'outils). `FlyoverController` tourne hors de React : à la lecture, il construit une fois un rail de caméra (`engine/cameraRail.ts`, fonctions pures, mis en cache par route et préconstruit à l'inactivité) — route rééchantillonnée à pas constant, courbe de vitesse de lecture (temps réparti selon la sinuosité et la pente à l'échelle de la caméra, vitesse de cap plafonnée, accélération relative bornée, facteur global résolu pour la durée visée `22 s·√(L/10 km)`), distance de caméra liée à la vitesse (flux à l'écran constant ; elle suit la vitesse lissée sur 2,5 s et limitée en variation à 6 %/s de zoom, `framingSpeedMps` — la vitesse brute chute à chaque virage serré et faisait plonger puis remonter la caméra en une seconde), ligne médiane / cap lissés à phase nulle (lissage du cap divisé par la rectitude² : les lacets suivent l'axe de la montée, les boucles et demi-tours ne font pas tourner la caméra), inclinaison selon le relief, et un poids hélicoptère (montées sinueuses comme l'Alpe d'Huez : lente orbite sur un petit arc autour de la cible, un peu plus haut et plus incliné ; le limiteur de cap réserve la vitesse de l'orbite). Une boucle rAF fait ensuite un travail en O(1) par image : `PlaybackTransport` (démarrage en douceur, décélération à la pause, freinage exact à l'arrivée, ressort de vitesse), pose de la FreeCamera (`setFreeCameraOptions`, inclinaison / cap tirés du vecteur œil → cible), garde-terrain (`queryTerrainElevation` le long de la ligne de visée, levée asymétrique), marqueur DOM de tête et traînée via `line-trim-offset` sur une source posée une fois (jamais de `setData` par image). L'approche / le saut / la reprise utilisent `flyTo` (fonctionne depuis le globe) puis un passage de relais à la FreeCamera ; la fin vole vers une vue d'ensemble de toute la route. La lecture élargit le FOV vertical à 44° via le `map.transform.fov` privé (`map/fov.ts`, animé pendant l'approche, restauré à la fermeture) et rapproche la caméra du même rapport (même cadrage et même LOD de tuiles). Une session montre la route seule : couches de POI supprimées (`setPoiLayersSuppressed`), tout autre marqueur et popup de la carte masqué par `[data-rv-flyover-session]` (`src/index.css`) sauf la tête (`data-rv-flyover-head`) ; réaffirmé chaque seconde et après un rechargement du style. Les interactions de carte sont suspendues et `map3d/lib/cameraOwnership` est posé tant qu'il possède la caméra (la rotation au repos et le menu contextuel s'effacent). React lit un store d'état (≤ 4 Hz) et un store de curseur du graphique (≤ 30 Hz, seul `AnalysisChartWithFlyoverCursor` se redessine) ; les clics sur le graphique / le tracé font un saut pendant qu'une session est ouverte. Les réglages vivent dans `flyover/config.ts` ; `npm run bench:flyover` simule la lecture à 30 / 60 / 144 i/s sur des routes synthétiques et réelles (Alpe d'Huez, Galibier) et échoue sur les régressions de vitesse / accélération de cap, de cadrage, de durée ou de dépendance à la fréquence d'images.

Son rAF est coupé (`_triggerFrame` ne fait que poser un drapeau) : la boucle d'export rend une image jusqu'à ce que Mapbox déclenche `idle` dans ce rendu (chaque tuile, source et étiquette), sans jamais rerendre tant que des tuiles manquent ; l'horloge de Mapbox est figée pendant un rendu et avancée d'1 s par rendu (toujours devant les horodatages réels des tuiles, fondus terminés au rendu suivant) et l'altitude moyenne (brouillard / horizon) est appliquée tout de suite au lieu d'être lissée (son lissage coûtait un second rendu 4K par image en mouvement). Après qu'une image a dépassé son délai (25 s), les suivantes attendent 3 s jusqu'à ce qu'une aboutisse. Elle recharge les tuiles de pente / d'altitude que le SW signale périmées, comme `listeners.ts` — jamais les tuiles DEM sur place (`_reloadTile` sur une tuile de terrain pouvait rester `reloading` pour toujours). `FlyoverVideoDirector` est le montage déterministe (vue d'ensemble de la route → approche de van Wijk → rail avec les lois du contrôleur au palier de vitesse de la barre d'outils + un recul de cadrage précalculé sur le rail (`framingScaleProfile` : lecture simulée une fois, recul dont la tête a besoin pour rester dans le cadre, maximum glissant sur ±4 s puis lissage sur 1,5 s — il commence avant un demi-tour et tient sur toute une section de lacets ; une garde réactive y entre et en sort) → arrivée → vue d'ensemble) ; un directeur éclaireur quelques secondes en avance précharge les tuiles suivantes dans le cache de tuiles de chaque source (`_preloadTiles` de Mapbox avec chaque tuile chargée adoptée par `_cache` au lieu d'être jetée — jetée, sa texture GPU fuyait ; bordures DEM recomblées quand une telle tuile est restaurée), au plus 16 tuiles par source et par appel et seulement dans une source sans rien en attente pour l'image courante (le S3 Terrarium est en HTTP/1.1 : 6 connexions, un préchargement en file devant une tuile à l'écran coûtait 5× le temps de rendu) ; chauffe par `fetch` en repli. Avant l'image 0 (« Préparation »), chaque tuile des 4 premières secondes (vue d'ensemble + approche, dix niveaux de zoom en deux secondes) est récupérée dans les caches HTTP / SW, borné à 45 s. Pas d'aperçu en direct : la boucle ne fait que rendre, capturer et encoder. La ligne de console de fin d'export (`[flyover-video] … i/s : N rendus …`) donne les rendus par image et les sources attendues par les images. Le portrait a son propre cadrage (`engine/framing.ts` : FOV vertical de 60°, avance de cible plus longue, ligne médiane tenue plus près). `npm run bench:flyover` vérifie le cadrage portrait et le montage (nombre d'images annoncé, continuité aux coupes).
- Les lignes de route (tracé, bordure, motifs de surface, sélection, traînée du survol) sont surélevées avec `line-elevation-reference: ground` + un petit dégagement (`itineraryPanel/lib/route-layer/routeElevation.ts`) : Mapbox lit alors, par tuile, la tuile DEM avec laquelle le maillage est dessiné. Jamais un profil de hauteur absolu (`sea`) tiré des altitudes de la route : les altitudes de sol nu s'enfonçaient sous le modèle de surface HD et masquaient jusqu'à la moitié du tracé visible, selon le niveau de zoom. Sous le zoom 6,5 (globe, où Mapbox saute les lignes surélevées), elles sont drapées ; la bascule suit `zoom`, pas `zoomend`. Les couches de l'itinéraire sélectionné sont réempilées au-dessus des autres routes (`stackActiveRouteOnTop`, plan pur dans `routeStacking.ts`, ne déplace que quand l'ordre est faux) : il lit le propre `_order` du style, que `moveLayer` modifie, jamais `style.order` (l'ordre de rendu : couches drapées d'abord, puis un tri par priorité 3D). Dans l'outil Tracer, chaque tracé visible peut être saisi (`routeEditPointer`, le sélectionné gagne là où des variantes se chevauchent) : en tirer un insère un point de passage et sélectionne cet itinéraire, un simple clic sur un autre tracé ne fait que le sélectionner ; tirer un marqueur de point de n'importe quel itinéraire le sélectionne aussi. Les marqueurs de carte qui doivent rester traversables au clic (`.rvi-analysis-hover-dot`) ont besoin d'un `pointer-events: none !important` en feuille de style : Mapbox réécrit le `pointer-events` en ligne d'un marqueur à chaque mouvement (`Marker#_evaluateOpacity`).
- Les POI d'itinéraire sont une seule couche symbol GPU (`features/poi/lib/poi-markers.ts`). **Ne jamais se fier au test de clic de Mapbox pour eux** : il teste toute l'image du sprite (marge transparente et ombres intégrées : un disque de 19 px dans une image de 66 px, une épingle dans une image de 88×126 px centrée sur sa pointe) et renvoie les symboles qui se chevauchent dans l'ordre des données, pas dans l'ordre de dessin (pas de `featureSortOrder` avec `symbol-sort-key`). Survol, clic, curseur et `queryPoiAtPoint` (Tracer, découpe de tracé, commentaires, survol du graphique) passent tous par `queryKeyAt` : Mapbox ne fournit que les candidats, puis le masque des pixels dessinés de chaque sprite (`poi-hit-mask.ts`, alpha ≥ 50 %, champ de distance de chanfrein) décide — pixel dessiné le plus haut, sinon le plus proche à moins de 3 px ; les données sont triées dans l'ordre de dessin. Favori ⇒ pause : mettre une étoile à un POI (popups de la carte, agenda, roadbook) pose aussi sa pause sur la ligne (`durationMin` : la durée Rythme de la catégorie, sinon 5 min), retirer l'étoile la retire, décocher la pause pose `0` (`ItineraryPanelContainer/poiFavoritePause.ts`, la règle unique). L'onglet « Agenda » du roadbook est l'identifiant de vue `'timeline'` (persisté, inchangé) : chaque position verticale y passe par `minuteToCanvasTopPx` (heures, grille, blocs, ligne de l'heure actuelle, glisser), l'en-tête d'un bloc est sur sa ligne du haut, et « Jusqu'au suivant » est le temps de selle jusqu'au point suivant dans le temps.
- `features/map3d` enveloppe Mapbox (terrain, couches WebGL personnalisées, `hooks/useMap/*`). La carte enregistre sa vue 500 ms après `moveend` ; cette valeur revient en `initialViewport` et `useMap` ignore son propre écho (il ne saute que vers une autre vue) — il ramenait en arrière tout vol de caméra lancé dans ces 500 ms. Les calculs lourds vivent dans des Web Workers / du WASM (LiDAR `.las/.laz` via `copc` + `laz-perf.wasm`, prédiction FIT). **Les gestionnaires `styledata` doivent être idempotents** (ne toucher le style que si quelque chose manque ou diffère) : chaque `styledata` vide le cache de drapé du terrain de Mapbox (toutes les tuiles proxy rerendues), et un gestionnaire qui modifie sans condition redéclenche `styledata` à l'image suivante — `moveLayer` salit le style même pour un déplacement sans effet, donc le réempilement de `useLidarSelection` à chaque `styledata` faisait restyler la carte à chaque image, jamais au repos. `TerrainManager.init()` n'appelle `setTerrain` que quand la source / l'exagération diffèrent (les gardes anti-carte plate l'appellent à chaque `styledata` / repos / battement de cœur). L'amorçage du style (`hooks/useMap/controller`) modifie le style une fois que Mapbox l'a analysé (`canMutateStyle`), jamais sur `isStyleLoaded()` (qui attend aussi le sprite, les TileJSON et les imports), et attend cette analyse sans échéance ; chaque garde-fou qui juge les progrès de Mapbox (style bloqué, forçage 3D, battement de cœur, échéance de chargement, vérification de rechargement…) tourne sur `controller/visibleClock.ts`, jamais sur un minuteur d'horloge murale : une page cachée (onglet en arrière-plan, fenêtre réduite ou couverte — Vite la recharge là quand une autre session modifie un fichier) ne reçoit aucune image d'animation, donc Mapbox n'analyse aucun style (`Style#loadJSON` en attend une), ne charge aucune tuile et n'est jamais au repos.
  `lib/styleLessMapGuards.ts` fait renvoyer `undefined` à `Map#getSource`/`getLayer` tant qu'aucun style n'a jamais été chargé (api.mapbox.com injoignable, jeton refusé ou absent) : Mapbox lisait `this.style.…` et levait une exception, ce qui faisait planter tout l'éditeur à un import GPX (trouvé par `e2e:journey` sans jeton).

### Typographie et densité de l'interface
- **Échelle typographique** : chaque taille de texte passe par `src/shared/styles/typography.css` (`--rv-font-size-2xs…4xl`, `--rv-font-sans`), dont l'en-tête contient la table des rôles (titre de panneau 16/600, section / onglet 14/600, libellé 13/500 atténué, valeur de contrôle / bouton / menu 13/600, barres d'outils compactes et grilles denses à 2 colonnes 12/500, légende 11, …). Ne jamais écrire de `font-size` littéral ni fluide (`vw`, `cqi`, `clamp`) dans une feature ; prendre le jeton du rôle. Le texte des canvas / sprites utilise `RV_FONT_SANS` (`shared/lib/typography.ts`). Rethink Sans est la seule police, servie par l'app (fichiers `@fontsource-variable/rethink-sans`, `@font-face` dans `typography.css`) — jamais Google Fonts : sa feuille de style bloquait le premier affichage derrière deux origines tierces et envoyait les IP des visiteurs à Google.
- **Densité** : le tableau de bord est rendu sur un canvas logique mis à l'échelle par `appScale` (`shared/lib/appScale.ts`). Règle : **jamais sous 1:1 sur un écran de densité standard** — un px CSS porte déjà la mise à l'échelle de l'OS et le zoom du navigateur, et réduire donnait du texte flou de 8 à 10 px sur les écrans non HiDPI (1080p en demi-écran, 1366×768, portables 1080p à 125–150 %). Jusqu'à la référence 1920×1080, l'interface est en 1:1, au-dessus elle grandit doucement (plafond 1,12). Exception Retina (`resolution ≥ 2dppx`, lue par une media query car `window.devicePixelRatio` est plafonné pour Mapbox dans `runtimeProfile.ts`) : sous la référence, l'échelle prend la moitié du déficit, plancher 0,85 (MacBook Air 13" ≈ 0,87, MBP 14" ≈ 0,89) — le 1:1 paraissait surdimensionné sur les MacBook et poussait les barres d'outils sur deux lignes. L'échelle est appliquée avec le `zoom` CSS (`appScaleStyle`, repli par transformation seulement là où `zoom` n'est pas standard), jamais `transform: scale()`, qui rééchantillonne le texte. Le visualiseur LiDAR applique la même échelle à ses panneaux flottants (`zoom: var(--app-scale)`). Les petites fenêtres se réorganisent à la place (`pages/Dashboard/lib/layout.ts`) : les panneaux latéraux rétrécissent, puis alternent (`resolveSidePanels` : le dernier ouvert reste) quand la colonne centrale passerait sous 560 px ; sous 846 px de hauteur (`isShortCanvas`), les outils de carte deviennent une grille de 2 colonnes de boutons de 32 px et le panneau central devient plus dense / plus court (240 px minimum). Sous 820×500, une surcouche « fenêtre trop petite » refermable s'affiche (`useIsMobileDevice`). Le plancher du texte est 11 px (`xs`) ; `2xs`/`3xs` sont réservés aux chiffres de badges et aux marqueurs de carte. Les barres d'outils ne passent jamais à la ligne : la recherche de la carte + les pastilles de filtre (`DashboardPlaceSearch` : le champ de recherche rétrécit d'abord, puis les libellés des pastilles avec une ellipse, puis les pastilles `--tight` ; les libellés ne disparaissent (`--icons`) que sur une scène de carte très étroite, p. ex. 1366 px avec les deux panneaux latéraux ouverts ; les paliers sont calculés à partir de la liste des pastilles, `PLACE_SEARCH_*_WIDTH`) et la barre d'outils d'analyse centrale (`useToolbarFitDensity`, 8 paliers mesurés finissant par une ellipse sur chaque libellé, texte complet dans `title`). `npm run bench:screens` (nécessite `npm run dev` : il utilise le compte de démo de dev) pilote le vrai tableau de bord dans Edge sans interface sur 15 écrans (1080p en demi-écran, portables à 125–150 %, MacBook, 1440p, 4K, ultralarge…) plus une fenêtre 1080p avec un panneau de gauche d'~800 px, et échoue sur tout texte sous 11 px (11 × 0,85 sur Retina), une mise à l'échelle par `transform`, une barre d'outils sur deux lignes, des panneaux qui se chevauchent / débordent, un menu / menu contextuel / redimensionnement non aligné sur le pointeur, un canvas Mapbox qui ne couvre pas son conteneur, ou des événements `styledata` émis pendant que la carte est au repos (boucle de mutation du style).
- **Mapbox sous le zoom du canvas** : GL JS mesure son conteneur avec `getBoundingClientRect()` et ne compense que les transformations CSS ; `map3d/lib/mapContainerZoom.ts` corrige `Map#_updateContainerDimensions` pour diviser par le `zoom` CSS effectif, si bien que la transformation, le canvas, `event.point` et `map.project()` sont tous en px de mise en page du conteneur de la carte (sans cela, la carte 3D couvrait appScale² de sa surface sur Retina). Le code qui place du DOM à partir de px de carte travaille en px de mise en page (`clientWidth`, `offsetWidth`, `event.point`), jamais avec les tailles de `getBoundingClientRect()` ; une distance mesurée sur un rectangle et passée à Mapbox (padding de caméra, `cameraFlight.ts`) est convertie avec `offsetWidth / rect.width`.
- **Dans le canvas**, les media queries de fenêtre et `vw`/`vh` mesurent le vrai écran, pas la mise en page : utiliser `@container rv-canvas (…)` et `var(--rv-canvas-width / --rv-canvas-height)`. Les surcouches rendues en portail dans `<body>` doivent soit lire l'échelle sur leur ancre (`readAppScale`) et se positionner avec `appScaledOverlayStyle` (schéma des listes déroulantes ; passer `inScaledLayer` quand le portail va dans un calque mis à l'échelle), soit utiliser `.rv-app-scaled-layer` (calques plein écran, `src/index.css`). Une barre d'outils qui peut déborder d'une colonne étroite défile horizontalement avec des fondus aux bords (`useHorizontalScrollOverflow`) ou passe à la ligne ; elle ne rogne jamais de contrôles.

### Thèmes (clair / sombre)
La « Préférence d'affichage » des réglages (système / clair / sombre, `displayMode` dans les réglages du gestionnaire de projets) est résolue par `shared/lib/appTheme.ts` (`initAppTheme()` dans `main.tsx` avant le premier rendu, `setAppThemePreference` depuis `SettingsPanel`, suit l'OS tant qu'elle est sur « système ») en `<html data-rv-theme="light|dark">` ; la valeur par défaut est « système ». Le sombre est le thème d'origine et garde ses valeurs exactes ; les jetons vivent dans `shared/styles/theme.css` (verre dans `glass.css`, menus dans `dropdown.css`). Règles de couleur dans les features : le texte, les filets et les remplissages translucides sont l'encre `rgb(var(--rv-ink) / α)` (blanc en sombre, #111114 en clair, même α), le texte plein `var(--rv-text)` ; le texte / les icônes sur le rouge ou une autre couleur pleine `var(--rv-on-accent)` (blanc dans les deux) ; une valeur propre à un thème est `light-dark(<clair>, <sombre>)` (`color-scheme` est posé avec le thème ; `light-dark()` ne prend que des couleurs, jamais une longueur ni un alpha). Ne jamais écrire de blanc / noir neutre littéral dans une nouvelle interface. Design du thème clair : panneaux de verre blanc (0,9) avec un `--rv-float-shadow` doux (jamais `none` : il se compose avec d'autres ombres), éléments en relief blancs sur un fond gris clair (`--rvi-tl-card-surface`), texte d'état dans les tons sombres (#b42318 / #b54708 / #067647), rouge de la marque et couleurs de données inchangés. Le contenu de la carte (marqueurs, leurs badges, lignes de route, étiquettes) est identique dans les deux thèmes ; popups, menus, légendes et cartes suivent le thème. Les icônes SVG monochromes blanches doivent être des masques peints avec `currentColor`/`--rv-text` (`AssetIcon`, `SvgV2Icon`), pas des `<img>` (les popups en chaîne HTML foncent les leurs avec une règle `filter: brightness(0)` du thème clair) ; le logo passe par `RedViewLogo`. Les couleurs des canvas / WebGL / Stripe lisent `useAppTheme()` (contour de pente du graphique, `stripeAppearance.ts`). Le visualiseur LiDAR reste sombre (il importe `theme.css` sans initialiser le thème).

### Pipeline de tuiles côté client (Service Worker)
`public/sw-dem.js` est une entrée mince qui fait `importScripts()` des modules sous `public/sw-dem/{core,sources,processing,swiss,norway,spain,runtime,workers}`. Il construit dans le navigateur des tuiles DEM, ortho, de pente et d'altitude à partir de sources publiques (IGN, AWS Terrarium, swissALTI3D, WCS de Norvège / d'Espagne) ; il renvoie 204 sur une vraie absence plutôt que de synthétiser des tuiles plates. Les tuiles DEM sont des PNG RGB avec le filtre Up compressés par le propre `zlibDeflateRle` du SW (`core/terrain-rgb.js` ; `CompressionStream` n'a pas de niveau et sa recherche de correspondances au niveau 6 est lente sur les surfaces bruitées à 0,40 m) : 1,7 à 3,3× plus rapides à encoder et 10 à 36 % plus petites que les anciennes tuiles RGBA non filtrées dans Chromium, mêmes altitudes (`test/service-worker/sw-dem-png.test.ts`, `bench:dem-sw`). Contrat : la page (`features/map3d/hooks/useMap/serviceWorker.ts`) enregistre le SW, attend `controllerchange`, et seulement ensuite ajoute les sources `/dem-tiles/` et `/ortho-tiles/`. Elle ne se recharge une fois que quand un worker d'une autre époque l'a servie au chargement (après un déploiement) : une première visite ou un nouvel onglet déjà sur le worker courant n'est jamais rechargé (il l'était, perdant les premières secondes de chargement de la carte ; `bench:dashboard -- --scenario sw`). **Quand vous changez quoi que ce soit sous `public/sw-dem*`, incrémentez le tampon de cache dans le commentaire d'en-tête de `sw-dem.js`** pour que les navigateurs voient une différence d'octets et purgent les anciens caches. L'invalidation de cache client équivalente pour l'app elle-même est `shared/lib/appCacheEpoch.ts` (`APP_CACHE_FIX_EPOCH` + identifiant de build tiré de `VERCEL_GIT_COMMIT_SHA`/`GITHUB_SHA`).

Sur le fond Satellite, `/vhr-tiles` (`sw-dem/sources/vhr-ortho.js`, attaché par `useMap/controller/vhrOrtho.ts` juste au-dessus de la couche `mapbox.satellite`, z18–21, toujours des tuiles de 512 px) superpose les orthos très haute résolution de l'IGN — `PCRS.LAMB93` 5 cm, puis `THR.ORTHOIMAGERY.ORTHOPHOTOS` 5–10 cm — via le WMS-R en EPSG:3857, et répond une tuile transparente ailleurs pour que Mapbox s'affiche (Mapbox Satellite en France est l'ortho IGN à 20 cm jusqu'à z19). `transformRequest` (`map3d/lib/satelliteTiles.ts`) force aussi les tuiles Mapbox Satellite `@2x` (GL JS ne les demande qu'à DPR ≥ 2, que le plafond de DPR de l'app atteint rarement) : les textures de drapé du terrain font 2× l'écran, et des tuiles de 256 px agrandies dedans perdaient jusqu'à ~20 % de netteté à certains zooms. Le WMS peint l'absence de données en **blanc pur** (le PNG est en RGB seulement, `TRANSPARENT`/`BGCOLOR` ignorés) : la couverture vient de masques z14 de 64 px par couche, et le blanc relié au bord est effacé sur la tuile elle-même.

Les surcouches de pente et d'altitude utilisent `TERRAIN_ALIGNED_RASTER_TILE_SIZE` (`map3d/lib/sources.ts`) pour que Mapbox demande exactement les tuiles de la pyramide DEM du terrain (`floor(zoom − 1)`) ; le SW lit alors la tuile DEM que le maillage 3D a déjà chargée. La surcouche d'altitude va plus loin : hors zone d'analyse, c'est une source personnalisée Mapbox (`altitude/lib/altitude-dem-source.ts`) qui réencode en mémoire la tuile DEM que le terrain a déjà décodée (`tile.dem`) — pas de second téléchargement (en source raster sur les mêmes URL, elle attendait derrière le terrain et arrivait 1 à 2 s plus tard), et elle recharge une tuile quand le terrain remplace son DEM ; seul le chemin masqué par zone utilise encore `/altitude-tiles`. Une surcouche de 256 / 512 px demanderait 1 à 3 niveaux de zoom plus profonds et forcerait le SW à construire sa propre pyramide DEM (16 à 64× le trafic IGN). Les tuiles de pente ne reçoivent jamais de substitut d'annulation : une tuile provisoire (voisine manquante, DEM de remplacement) est reconstruite quand le DEM arrive (`notifySlopeDemTileReady` → `SLOPE_TILES_STALE` → la page recharge la source).

### i18n
Les textes de l'interface **sont le texte source français / anglais lui-même** : les composants appellent `t('Texte français ou anglais')` (`useAppI18n`) ou `translateAppText(...)` ; les traductions sont des paires `{ fr: '...', en: '...' }` dans `src/shared/i18n/config/translations/*.ts`. `AppI18nProvider` traduit en plus les nœuds texte du DOM et les attributs `aria-label`/`placeholder`/`title` via un MutationObserver, donc un nouveau texte visible a besoin d'une paire, sinon il ne sera pas traduit. La couche API utilise `api/_lib/translations-data.ts`, **produit** par `scripts/build/prebuild-api-i18n.mjs` (extrait par regex les littéraux `{ fr: '…', en: '…' }` de chaque fichier de `translations/` sauf `index.ts`) — ne pas le modifier à la main, et garder les paires en littéraux d'objet unique avec des chaînes entre guillemets (pas de gabarits littéraux) pour que la regex les trouve encore. Un fichier de paires par domaine (`global`, `dashboard`, `itinerary`, `lidar`, `map`, `app`, `auth`, `fitPredictor`, …) ; un nouveau fichier doit aussi être étalé dans `translations/index.ts`. Sur une clé en double, la dernière paire l'emporte, mais les clés de la langue elle-même battent toujours celles de l'autre langue (un texte déjà dans la langue cible reste lui-même, typographie comprise : apostrophe courbe, espace insécable). Le traducteur du DOM ne reconnaît que des nœuds texte entiers : un gabarit littéral (`` `${n} fichiers` ``) ne se traduit jamais — utiliser `t('{{count}} fichiers', { count: n })` ; les chaînes de canvas / WebGL / text-field Mapbox ont besoin de `translateAppText` explicitement. Le visualiseur LiDAR (`viewer.html`, sans React) exécute le même observateur du DOM (`shared/i18n/domTranslation.ts`) depuis `lidar/viewer/main.ts`. `npm run i18n:audit` (`scripts/quality/i18n-audit.mjs`, `--list` pour le détail) rapporte la couverture, les textes manquants, les gabarits littéraux intraduisibles et les paires en conflit ; `npm run i18n:check` (le même en `--strict`, dans `npm run check`) échoue sur le moindre texte manquant ou conflit.

## Conventions de build / TypeScript
- Alias de chemin `@/*` → `src/*` (tsconfig + Vite).
- `tsconfig.app.json` est strict avec `noUnusedLocals`, `noUnusedParameters`, `verbatimModuleSyntax` (utiliser `import type`) et `erasableSyntaxOnly` (pas d'`enum`, d'espaces de noms ni de propriétés de paramètres de constructeur).
- Environnement : les variables exposées au navigateur sont `VITE_*` ; les secrets réservés au serveur (Stripe, clé d'API Appwrite, URL des services amont) sont lus dans `process.env` dans `api/`. `.env` est ignoré par git — partir de `.env.example`.
- `.claudeignore` (local, ignoré par git) exclut `node_modules`, `dist`, `vendor/redviewalgo/target`, images / wasm et les grosses données géographiques (`public/france-border.json`, icônes de POI, etc.).
