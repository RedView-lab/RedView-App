# 2026-09-18 — RedView

## Fix : artefact de "peigne" horizontal sur les tuiles 3D / pentes (IGN DEM)

**Symptôme** : la couche pente (et la tuile DEM qui l'alimente) affichait des tirets
horizontaux réguliers ("peigne") sur tout le relief.

**Cause racine (mesurée, pas supposée)** : le WMS IGN (`data.geopf.fr/wms-r/wms`,
`CRS=EPSG:4326`) était interrogé avec une géométrie *carrée en degrés*
(`WIDTH === HEIGHT === 256`). Les produits IGN sont stockés sur une grille **carrée en
mètres**, qui en EPSG:4326 est `1/cos(lat)` plus large que haute. Le serveur
rééchantillonne alors les lignes en plus proche voisin et **duplique `1 - cos(lat)`**
d'entre elles :

| latitude | prédit `1-cos φ` | mesuré |
|---|---|---|
| 42.8° | 26.6 % | 26.27 % |
| 45.1° | 29.4 % | 29.41 % |
| 48.3° | 33.5 % | 33.33 % |

Horn lit `∂z/∂y` sur deux lignes adjacentes → le gradient alterne entre 0 et ~2× la
valeur réelle → la rampe `raster-color` peint des tirets horizontaux.

**Correctif** (`public/sw-dem/sources/ign-fetcher.js`) :
1. `mnsWmsRequestSize()` — requête **carrée en mètres** : `WIDTH = round(256/cos φ)`,
   `HEIGHT = 256`. Mesuré : lignes dupliquées 29.4 % → **0.00 %**, comb 0.018 → 0.000.
2. `mnsWmsResampleToTile()` — moyenne de boîtes X-aware NaN vers 256².
3. `decombDuplicateRows()` — filet de sécurité : interpole toute suite de lignes
   bit-identiques (inverse exact d'un sur-échantillonnage nearest-neighbour).
4. **Repli MNS-correl supprimé** : `HIGHRES(.MNS)` n'est servi qu'à 2× en Y
   (128 lignes distinctes / 256), quel que soit le CRS (testé 4326 **et** 3857), avec
   des lignes non appariées → comb 0.70–1.23. On retourne `null` et `buildIGNTile`
   retombe sur le chemin WMTS (matrice de tuiles native WGS84G, aucun ré-échantillonnage).
5. Épochs de cache bumpés : `2026-09-18-lidar-wms-aspect-v2` (config.js + sw-dem.js +
   `src/shared/lib/appCacheEpoch.ts`).

**Vérifié** : code patché exécuté en sandbox VM contre le serveur IGN réel →
`eqY = 0.00 %` sur Pyrénées / Alpes / Vosges, 65536/65536 pixels valides, altitudes
correctes. `eslint` + `tsc -b` OK.

**Diagnostic réutilisable** : `scripts/diagnose-wms-row-comb.mjs`
(`node scripts/diagnose-wms-row-comb.mjs [lng lat zoom]`).

## Conventions projet notées
- Les modules du service worker (`public/sw-dem/**`) sont du JS chargé par
  `importScripts` — pas de modules ES, tout est dans le scope global du SW.
- Le WMS IGN est **rate-limité** (HTTP 429) : espacer les requêtes dans les scripts de test.

## Suite — vérification zooms + fausses pistes (ne pas re-chercher)

- Le correctif tient à **tous** les zooms (z13→z17) : `eqY` 29,4 % → 0,00–0,40 %,
  `distinctRows` 181/256 → 256/256, comb 0,01–0,03. Mesuré via sandbox VM sur le
  serveur IGN réel (`getMnsWmsTile` patché).
- **Fausse piste écartée** : le sous-échantillonnage du MNS 0,40 m. Testé en demandant
  256 / 512 / 724 / 1024 lignes sur la même tuile : les valeurs de colonne sont
  **stables** → la requête 256 lignes est fidèle, pas d'aliasing. Ne pas ajouter de
  supersampling (coût ×4 pour rien).
- **Fausse piste écartée** : EPSG:3857 (pire : comb 0,67) et EPSG:2154 (couche non
  publiée → tuile constante).
- **Attention** : le versant de l'Alpe d'Huez (z15, ~6,07 N/45,09 E) présente des
  ondulations **réelles** (pistes de ski, murs) — ce n'est pas l'artefact. Bon site de
  test : Alpes 6,05/45,05 z14, ou Plateau de Valensole 5,98/43,83.
- **Piège d'exploitation** : après un changement du pipeline DEM, un simple F5 ne suffit
  pas toujours — l'ancien Service Worker reste actif et ressert les tuiles de
  CacheStorage. Forcer : unregister les SW + vider les caches + localStorage
  (`redview:app-cache-epoch`) puis recharger.
- Chemin worker (`slope-pool.worker.js`) audité : sain, il réutilise `slope-math.js`.
  À noter pour plus tard : son LRU de DEM décodés est clé `z/x/y` **sans le profil**
  (risque de mélange `default` / `terrain`).
- **Fausse piste écartée** : `raster-resampling: linear` et le filtre Sub du PNG
  encodeur — round-trip PNG Sub vérifié correct.
