## Bug corrigé — un clic sur la carte ouvrait un onglet Google Search

**Symptôme rapporté** : « quand je clic/glisse sur la carte ça lance un popup url Google
search avec le nom du lieu cliqué » — navigation carte aux étiquettes, clic sur un parc

navigue plus nulle part. `mousedown`/`mouseup` conservés : ils servent au garde-fou du
survol pendant un drag.

`openGoogleSearchForPoi` est **laissé exporté** : il n'est appelé nulle part (vérifié par

## Bug corrigé — à la création, la caméra « spawn collée au terrain »

**Symptôme rapporté** : « quand je spawn, je spawn collé au terrain, au lieu d'un zoom
beaucoup plus global » (capture : vue à l'échelle de l'Europe, bien plus large que la vue
France de `DEFAULT_VIEW`).

**Cause racine** (chaîne complète) :
1. `createDefaultProject()` ne renseignait **jamais** `dashboard.mapViewport`.
2. `useDashboardChrome.ts:111` fait `setProjectMapViewport(dashboard?.mapViewport ?? loadViewport())`
   → `dashboard.mapViewport` étant `undefined`, on tombait sur `loadViewport()`, la valeur
   **globale** de `localStorage` (`redview-map-viewport`), celle laissée par le **projet
   précédent** (dernier pan/zoom de l'utilisateur, donc souvent très zoomé et incliné).
3. Ce viewport partait dans `MapView.initialViewport` → `useMap`, qui ne retombe sur
   `loadViewport()` **que** si `initialViewport` est `null` — donc la valeur périmée était
   bien celle utilisée, et `DEFAULT_VIEW` n'était jamais lu.

**Correctif** : `createDefaultProject()` amorce désormais `dashboard.mapViewport` depuis
`DEFAULT_VIEW` (+ import `DEFAULT_VIEW` depuis `../../../map3d/lib/mapbox.config`).
`mapbox.config.ts` est un module **feuille** (aucun import) → pas de risque de cycle.

**Persistance du viewport = 2 endroits** (à retenir) : le projet
(`project.dashboard.mapViewport`) **prime**, avec repli sur le global `localStorage`
(`redview-map-viewport` via `loadViewport()`). Conséquence : seuls les **nouveaux** projets
adoptent `DEFAULT_VIEW` ; un projet existant garde la caméra qu'il a sauvegardée.

Vérifié : `tsc -b` exit 0 ; `eslint` sur `defaultState.ts` → 0 erreur ; corps final de

## Échelle typographique globale (texte trop petit sur Mac)

**Demande** : « augmenter l'échelle globale de toute la taille de typo (sur mon Mac c'est
trop petit) ».

**Cause racine (mesurée)** : tout le CSS est écrit en `px` **codés en dur** (0 occurrence
de `rem` sur ~3818 longueurs) sur un canvas de design 1920×1080, puis réduit uniformément
par `appScale = min(w/1920, h/1080) * 0.86`, plafonné à **0.86** (`APP_SCALE_MIN` 0.45 /
max 0.86). Résultat sur les écrans réels :

| Écran | appScale | 14 px déclaré → rendu |
|---|---|---|
| MacBook Air 13" (1470×956) | 0.658 | **9.2 px** |
| MacBook Pro 14" (1512×982) | 0.677 | **9.5 px** |
| MacBook Pro 16" (1728×1117) | 0.774 | **10.8 px** |
| Écran externe 2560×1440 | 0.86 (plafonné) | **12.0 px** |

→ sous le seuil de lisibilité (~11 px). Augmenter `appScale` est **impossible** : il est
plafonné et il est porteur pour la géométrie du layout (un scale plus grand ⇒ canvas de
design plus étroit ⇒ panneaux latéraux rognés).

**Solution** : décorréler l'échelle de la *typo* de celle du *layout* via un `zoom` sur un
canvas de typographie dédié.

- `src/pages/Dashboard/lib/constants.ts` : ajout de `TYPOGRAPHY_SCALE = 1.25` et
  `APP_SCALE_MAX = 0.86` (le littéral `0.86` était dupliqué dans `layout.ts`).
- `src/pages/Dashboard/components/TextScaleCanvas.tsx` (**nouveau**) : wrapper `zoom:
  1.25`, `width: 100/1.25 %`, `height: 100/1.25 svh`, et publie `--rv-type-scale`.
- `src/pages/Dashboard/index.tsx` : le contenu est enveloppé dans `<TextScaleCanvas>`.
- `src/pages/Dashboard/lib/layout.ts` : `0.86` → `APP_SCALE_MAX`.
- `src/index.css` : règle `.rv-text-scale` (+ `.rv-fixed-viewport`, voir plus bas).

**Pourquoi `zoom` et pas `transform: scale()`** : `zoom` est *layout-affecting* (le
navigateur reflue, et **les longueurs `px` se mettent à l'échelle linéairement**) → un seul
constante relève les 3818 `px` du code sans éditer chaque fichier. Il préserve aussi le
hit-testing et la mesure du conteneur Mapbox, ce qu'un `transform` casserait.

Résultat : 1.25 relève le MBP 14" de ≈9.5 px à **≈11.9 px**. La formule `100/scale`
compense exactement, donc le canvas remplit la vue au pixel près sur tous les écrans
(vérifié par calcul : 100 % × 100 %, aucun débordement) — le `overflow: hidden` des
ancêtres n'a rien à rogner.

## Bug induit puis corrigé : overlays `position: fixed` dans le canvas zoomé

**Symptôme** (capture utilisateur, « problème sur google là ») : à la création d'un projet,
la page de chargement noire ne couvrait plus l'écran — le gestionnaire de projets
réapparaissait sur le bord droit et en bas.

**Cause** : un ancêtre **transformé** (`transform: scale()` du canvas dashboard) ou
**zoomé** (`zoom` du canvas typo) devient le *containing block* des descendants
`position: fixed`. Donc `inset: 0` portait sur la boîte du **canvas**, elle-même ensuite
mise à l'échelle ×0.478 **et** zoomée ×1.25 → l'overlay devenait plus petit que l'écran.

**Correctif** : nouvelle classe utilitaire `.rv-fixed-viewport` dans `src/index.css`
(`width/height: calc(100% / var(--rv-type-scale, 1))` — `100%` se résout sur le canvas, qui
est exactement la boîte à couvrir). **Piège évité** : ne pas mélanger `100%` (espace canvas)
et `100dvh` (espace viewport réel) — les deux axes doivent être dans le *même* espace, sinon
la hauteur est fausse.

Appliquée à : `DashboardProjectLoading`, `rvi-panel-fullscreen-root` (timeline plein écran),
`rv-modal-backdrop` (code de vérification), `rv-mobile-block-overlay`,
`rvpb-billing-page` (×2 dont la fallback d'erreur). Les `inset: 0` correspondants ont été
retirés des CSS.

**À retenir — ce qui n'est PAS affecté** : les popovers positionnés en JS
(`rvi-itin-actions-menu`, `AddItineraryDialog`, palettes de couleurs) utilisent
`createPortal(..., document.body)` → ils sortent de `#root`, donc hors du canvas zoomé et
hors de son `transform`. Leurs coordonnées `getBoundingClientRect()` restent correctes.
`#overlay` de `viewer.html` (visualiseur LiDAR) est une page autonome, hors app React —
laissée intacte.

Vérifié : `tsc -b` exit 0 ; `eslint` sur les fichiers touchés → **aucune** erreur nouvelle
(seules subsistent les 2 erreurs pré-existantes : `Dashboard/index.tsx:169`
`set-state-in-effect`, et `VerificationCodeModal.tsx:149,171` `no-explicit-any`) ;
couverture écran vérifiée par calcul sur 4 viewports (dont celui de la capture, 1080×600).
